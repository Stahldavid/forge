# S1.3 — Proof & Conformance: Scope and Gate

**Record ID:** `AF-S1.3-SCOPE-2026-09-11`

**Status:** `PLANNING_PROPOSAL`

**Baseline:** `main@d2f426b1577d457bc6609c4d8e88ef7a055a1a23`

**Authority:** proposed documentary scope only. This record does not authorize S1.3
implementation, new test/tooling infrastructure, runtime changes or P0b.

## 1. Proposed objective and provenance

S1.1 defines the accepted operation/invariant obligations. S1.2 maps those obligations to
exact implementation components, state ownership, trust inputs, event families and existing
evidence. S1.3 is proposed as **Proof & Conformance**: make every accepted conformance claim
traceable to explicit evidence with exact source/execution coordinates, reproducible
procedures, result status, limitations and a visible gap disposition.

For this slice, **proof** means a reviewable conformance argument backed by repository
artifacts, source mappings and executed evidence. It does not imply mathematical proof,
cryptographic proof or formal verification unless one of those mechanisms is later scoped,
implemented and separately adopted.

The S1.1 conformance plan explicitly left the following as later candidates rather than
requirements: a generic protocol conformance runner, formal state-machine/model checking,
proof-artifact signing, cross-language harnesses and production evidence retention. S1.3
therefore starts by organizing and reproducing the evidence already available. No tooling
category is preselected merely because the slice is named Proof & Conformance.

## 2. Frozen inputs and precedence

S1.3 planning consumes, without silently rewriting:

- adopted S1.0B1/B2 decision/evidence freezes and P0a acceptance record;
- adopted S1.1 scope, normative kernel, conformance matrix and adoption record;
- adopted S1.2 scope/design plan, reference design, implementation traceability and
  decision/finding register, plus the completed S1.2 adoption event documented by the
  proposed `S1.2_ADOPTION_RECORD.md` in this package;
- separately adopted S12-F01 and S12-F02 repair evidence;
- the existing executable tests, schemas, workflows and exact historical workflow results
  referenced by those records.

The README precedence and supersession rules continue to apply. A later reproduction can
add evidence about a current SHA; it cannot rewrite what an earlier reviewed SHA did or did
not prove. Historical acceptance evidence remains bound to its historical subject and
execution coordinates.

If S1.3 discovers a semantic defect or mismatch, it must be classified through the existing
clarification/compatible-repair/extension/supersession process. A proof document or runner
cannot manufacture authority or redefine an `OP-*`/`I-*` obligation.

## 3. In-scope questions

The first S1.3 work must answer, individually and source-linked:

1. What existing evidence supports each of the **24** adopted `OP-*` rules and each of the
   **35** adopted `I-*` invariants?
2. Which of the **16** persisted event families has positive, negative, replay and
   structural evidence, and where is that evidence located?
3. Which exact code/document SHA is the subject of each claim, and which exact SHA was
   actually executed or reviewed?
4. Was the observation produced by a GitHub workflow, a local clean worktree, a captured
   dirty-worktree state, static/source inspection, or a historical acceptance record?
5. What exact command/test/workflow, environment and expected observation reproduce it?
6. Is the result `PASS`, `FAIL`, `SKIPPED`, `NOT_APPLICABLE`, `BLOCKED` or `INCONCLUSIVE`?
7. What claim does the evidence support, what does it **not** support, and what trust or
   applicability assumption remains external?
8. Where are the real gaps: missing metadata, missing reproduction, missing negative vector,
   environment variance, structural-only coverage, explicit assumption/direction, or an
   actual conformance failure?
9. Does any observed gap justify new tooling? If so, what minimal mechanism is necessary,
   and why can the need not be satisfied by existing tests/workflows plus a documentary
   evidence catalog?

## 4. Proposed first implementation stage: S1.3-A

After this planning package is independently reviewed and adopted, the first proposed
implementation stage is deliberately limited to **Evidence Registry & Reproduction
Baseline** (`S1.3-A`). It may:

- inspect existing code/tests/docs/workflow history;
- execute existing repository tests/workflows or focused existing test files;
- record exact commands, environments, run IDs, SHAs, outputs and limitations;
- organize existing evidence into stable records by OP/I/event;
- classify and prioritize gaps;
- recommend, but not implement, later tooling where a concrete gap demonstrates need.

S1.3-A does **not** authorize new runtime behavior, schema changes, test rewrites, new
workflows, dependency additions, timeout changes, a generic runner, model checker, proof
signing, cross-language harness, persistence service or provider execution. If a missing
vector or defect requires code/test/tooling changes, S1.3-A records that as a gap and a
separate scoped change must be authorized.

### Required future S1.3-A deliverables

| Artifact | Required content |
| --- | --- |
| `S1.3_EVIDENCE_CATALOG.md` | Stable evidence IDs; exact subject/execution/adoption coordinates; command/workflow/source reference; environment; result; supported claim; limitations and provenance. |
| `S1.3_CONFORMANCE_MATRIX.md` | One row per 24 OP and one row per 35 I, plus event-family cross-index; existing evidence IDs, applicability, current evidence disposition and gap references. |
| `S1.3_REPRODUCTION_PROTOCOL.md` | Rules for exact-SHA reproduction, clean/dirty worktree handling, workflow/local evidence, retries, timeouts, environment capture and result normalization. |
| `S1.3_GAP_AND_TOOLING_REGISTER.md` | Classified gaps, blocking impact, minimum evidence needed to close them and explicit decisions on whether any later tooling category is justified. |

No machine-readable evidence manifest is required by this planning record. If S1.3-A shows
that a machine-readable catalog is necessary for consistency or automation, that need must
be recorded before adopting a schema or generator.

## 5. Evidence model

### 5.1 Evidence kinds

Each evidence record must be one of these kinds, without conflating them:

- `HISTORICAL_ACCEPTANCE_EVIDENCE` — exact reviewed-head/merge/workflow evidence already
  used in an adopted acceptance decision;
- `CURRENT_REPRODUCTION_EVIDENCE` — an executed observation on the stated current subject;
- `SOURCE_MAPPING` — source/symbol inspection, such as the adopted S1.2 traceability map;
- `STRUCTURAL_EVIDENCE` — schema/type/shape existence without a behavioral execution claim;
- `ASSUMPTION` — trusted applicability input not proven by the finite repository corpus;
- `DIRECTION_ONLY` — frozen architecture direction outside executable P0a conformance.

An evidence kind is not a result status. A source mapping cannot be reported as a passing
execution, and an assumption cannot be converted into proof by documentation alone.

### 5.2 Executed result statuses

Executed evidence must use exactly one of:

- `PASS` — the stated expected observation was obtained for the bound execution state;
- `FAIL` — the stated expected observation was not obtained;
- `SKIPPED` — the test/job existed but intentionally did not execute;
- `NOT_APPLICABLE` — the check does not apply to the scoped change/claim, with reason;
- `BLOCKED` — execution could not proceed because a named prerequisite was unavailable;
- `INCONCLUSIVE` — execution occurred but variance, timeout, environmental uncertainty or
  insufficient observation prevents a pass/fail conformance claim.

A retry does not erase a prior `FAIL`, `BLOCKED` or `INCONCLUSIVE` observation. Every
attempt used as evidence must remain visible with its provenance.

### 5.3 Minimum evidence record

Every S1.3-A evidence record must resolve:

```text
evidence_id
claim_ids[]                  # OP-*, I-* and/or event family
kind
source_or_test_ref
subject_sha                  # source state the claim is about
execution_sha_or_state       # exact commit or captured worktree state actually observed
adoption_merge_sha           # optional historical acceptance coordinate
command_or_workflow
working_directory
runtime_and_environment      # OS/tool versions or workflow job/matrix identity
expected_observation
actual_observation
result_status
artifact_log_or_run_ref
reproduction_status
limitations[]
provenance_notes
```

For static `SOURCE_MAPPING`, fields that require execution are `NOT_APPLICABLE`, not
silently omitted. For a local run to be called exact-SHA evidence, the worktree must be
clean at that SHA. Otherwise the evidence must identify the captured diff/state and cannot
claim to represent the bare commit alone.

## 6. Gap model

S1.3-A must classify each unresolved item as one of:

| Gap class | Meaning |
| --- | --- |
| `EVIDENCE_METADATA_GAP` | evidence exists but exact SHA/run/command/environment/claim binding is incomplete |
| `REPRODUCTION_GAP` | a claimed observation lacks a sufficient reproduction procedure or cannot currently be reproduced |
| `NEGATIVE_VECTOR_GAP` | positive behavior exists but an applicable adversarial/negative obligation lacks direct evidence |
| `ENVIRONMENT_VARIANCE_GAP` | results differ materially across environment/attempt and the claim cannot yet be stabilized |
| `STRUCTURAL_ONLY` | intentionally structural coverage, such as the adopted `I-PLAN-004` executable boundary |
| `ASSUMPTION` | external trust/applicability input intentionally not proven by the corpus |
| `DIRECTION_ONLY` | frozen future direction, not an executable conformance obligation |
| `TOOLING_CANDIDATE` | an observed evidence-management/proof gap may justify new tooling, but need and scope are not yet adopted |
| `BLOCKING_GAP` | an applicable conformance claim cannot currently be made responsibly; it blocks that claim/promotion, not adoption of an accurate evidence inventory that records the gap |

`STRUCTURAL_ONLY`, `ASSUMPTION` and `DIRECTION_ONLY` preserve adopted applicability; they are
not defects to be hidden or automatically converted into tooling work. A `BLOCKING_GAP`
must remain visibly attached to the affected claim until separately closed; S1.3-A is
allowed to adopt that fact as part of a truthful evidence baseline.

## 7. Tooling decision boundary

S1.3 planning deliberately does not choose tooling. S1.3-A may recommend a later decision
only when an observed gap identifies a concrete need.

| Tooling candidate | Minimum justification before separate implementation scope |
| --- | --- |
| Generic conformance runner | repeated manual evidence execution/binding demonstrably causes inconsistency or cannot scale after the evidence/reproduction record shape is stable |
| Formal state-machine/model checking | a named finite-state/concurrency invariant lacks adequate executable evidence and a proposed abstraction can be traced back to S1.1 rules without redefining them |
| Proof/evidence signing | an explicit threat model requires provenance/integrity beyond the currently trusted repository/workflow record, including key lifecycle and verifier semantics |
| Cross-language conformance harness | a second implementation/language or an adopted cross-language canonical profile exists; current JS/TS P0a and non-JCS profile alone do not justify it |
| Production evidence retention service | an explicit durability, audit or compliance requirement exists beyond repository/workflow retention |
| Machine-readable evidence manifest | manual/documentary records prove insufficient for consistent automation and a schema can be adopted without turning evidence metadata into protocol authority |

A tool may improve evidence handling; it cannot grant runtime authority or make a failing
protocol implementation conformant.

## 8. Non-objectives and exclusions

This planning PR and S1.3-A do not authorize:

- P0b or any real nondeterministic/provider adapter;
- production storage, outbox, failover, recovery epochs or consequential effects;
- changes to the accepted S1.1 semantics, operation IDs, invariant IDs or event families;
- a new canonical profile or JCS migration;
- broad runtime/security certification;
- automatic promotion from a test result to production readiness;
- replacing `ASSUMPTION`, `STRUCTURAL_ONLY` or `DIRECTION_ONLY` with stronger claims;
- silent exclusion of failing evidence, undocumented retries or cherry-picking only green
  attempts;
- treating generated prose, diagrams or model outputs as authority or independent evidence.

P0b remains explicitly outside scope.

## 9. Gate for adopting this planning package — S13-P

This planning package can be adopted only when:

| Gate | Requirement |
| --- | --- |
| S13-P01 | S1.2 adoption coordinates, reviewed head, merge parents/tree and exact-head evidence are accurate; historical records remain unchanged. |
| S13-P02 | S1.3 objective and the limited S1.3-A first stage are explicit; `proof` is not overstated as formal/cryptographic proof. |
| S13-P03 | Future S1.3-A deliverables and the full 24 OP / 35 I / 16 event inventory requirement are explicit. |
| S13-P04 | Evidence kinds, executed result statuses, exact-SHA/worktree binding and minimum record fields are defined. |
| S13-P05 | Gap classes distinguish missing evidence from intentional structural/assumption/direction applicability. |
| S13-P06 | Generic runner, model checking, signing, cross-language, retention and machine-readable automation remain separate tooling decisions, not implied implementation work. |
| S13-P07 | Applicable repository checks pass on the exact final planning SHA; path-filtered non-triggered jobs are `NOT_APPLICABLE`; local limitations are disclosed without false green claims. |
| S13-P08 | Independent exact-SHA review reports zero unresolved BLOCKER/HIGH/MEDIUM, followed by an explicitly authorized merge to `main`. |

Merging the planning package adopts only the **S1.3 scope, evidence model, S1.3-A proposal
and gates**. It does not itself create the four S1.3-A deliverables or authorize tooling.

## 10. Gate for the future S1.3-A evidence baseline

A future dedicated S1.3-A PR can be adopted only when:

| Gate | Required evidence |
| --- | --- |
| S13-A01 | exact adopted S1.3 planning baseline and exact evidence-subject baseline identified; relevant baseline movement assessed |
| S13-A02 | all four S1.3-A artifacts exist and use stable evidence/gap IDs |
| S13-A03 | every one of the 24 OP and 35 I entries is individually present; all 16 events are cross-indexed; no orphan accepted rule |
| S13-A04 | every executed evidence record binds exact source/execution state, command/workflow, environment, expected/actual observation, result and provenance |
| S13-A05 | historical acceptance evidence is distinguished from current reproduction and source/structural evidence |
| S13-A06 | `FAIL`, `SKIPPED`, `NOT_APPLICABLE`, `BLOCKED` and `INCONCLUSIVE` observations are retained and not normalized into pass |
| S13-A07 | reproduction procedures cover existing applicable evidence or record an explicit reproduction gap |
| S13-A08 | all remaining gaps have a class, affected OP/I/event, blocking impact and minimum closure evidence |
| S13-A09 | no unclassified applicable gap; every `BLOCKING_GAP` is explicitly attached to affected claims, which must not be summarized as `SUPPORTED` or full conformance until separately closed |
| S13-A10 | tooling recommendations, if any, remain proposals with explicit need; no new runner/model/signing/interoperability/retention implementation is bundled |
| S13-A11 | documentary/evidence-organization diff only; execution of existing checks is allowed, but no runtime/schema/test/workflow/dependency/timeout semantic change |
| S13-A12 | applicable exact-final-SHA repository checks and independent review have zero unresolved BLOCKER/HIGH/MEDIUM, followed by explicitly authorized merge |

Adopting S1.3-A establishes a trusted repository evidence/reproduction baseline. That
baseline may honestly contain `BLOCKING_GAP` entries; their presence blocks the affected
conformance claim or later promotion, not adoption of the cataloged evidence state itself.
The gap/tooling register must inform any next objective and acceptance gate. S1.3-A still
does not automatically authorize a subsequent tooling stage.

## 11. Exit condition of this planning record

This planning record is complete when the repository can begin a later S1.3-A PR with:

- a fixed baseline and precedence model;
- a fixed 24 OP / 35 I / 16 event inventory obligation;
- stable evidence kinds and result statuses;
- exact evidence/provenance fields;
- a reproduction contract;
- a gap taxonomy;
- explicit tooling decision boundaries;
- separate S13-P and S13-A acceptance gates.

Until S13-P08 is satisfied, S1.3 remains unadopted. Until S13-A12 is later satisfied, no
S1.3 evidence baseline is adopted; if that baseline contains `BLOCKING_GAP` entries, no
stronger conformance claim may ignore them. P0b remains unauthorized throughout.
