**Record ID:** `AF-S1.1-KERNEL-2026-09-08`

**Planning baseline:** `main@3a0ce40ffe31555709d213bf06d674c62f28ad32`

## 1. Applicability and authority of this record

This candidate specifies the accepted JavaScript/TypeScript, in-memory P0a protocol.
SHALL, SHALL NOT and MAY describe conformance to that target. They do not grant runtime
authority or adopt this record. The precedence and supersession rules in the governance
README still apply. The adopted freezes and planning records are unchanged.

The public conductor and replay entrypoints are the exports of
`src/forge/agent-fabric/index.ts`: `hardened-conductor.ts` and `hardened-reducer.ts`.
The underlying `conductor.ts` and `reducer.ts` are implementation components, not alternate
authority paths. Pure exported helpers do not confer the public conductor's guarantees.

Applicability requires:

- **T-001, ASSUMPTION:** a trusted journal origin and complete accepted prefix. A valid hash
  chain establishes internal integrity, not storage provenance or absence of truncation.
- **T-002, ASSUMPTION:** a trusted, deterministic `OwnerAuthorizationVerifier`, including
  offline `verifyRecorded`. Synthetic test verification is not production authentication.
- **T-003, ASSUMPTION:** trusted resource definitions, stable clock semantics and the trusted
  semantic control path. Workers cannot replace these inputs with their own declarations.
- **T-004:** content identity is necessary where required, but never sufficient authority.

No claim is made for arbitrary live JavaScript objects, Proxy trap semantics, authenticated
production storage, production transactions/outbox, provider execution, target effects,
reconciliation, recovery epochs, routing, persistent memory or evolution. P0b remains
deferred and unauthorized. Read-only target semantics, the full Trusted Privilege Domain,
AHCP decomposition and the full Harness Compiler remain `FROZEN_DIRECTION`, not newly
executable P0a obligations.

The 24 `OP-*` identifiers below retain the adopted planning IDs and serve as rule IDs.
Each operation record incorporates this section, sections 3–6 and its conformance catalog
row. This explicit inheritance supplies the 17 fields required by the scope/gate:

| Required field | Location / inherited value |
| --- | --- |
| Rule ID | operation heading; identical `rule_id` and `operation_id` |
| Invariant references | operation record and individual invariant matrix |
| Inputs; trusted inputs; state read-set | operation record; T-001/002/003 apply to control operations |
| Preconditions; authority requirement | operation record, structural admission and exact binding below |

| Rejection result | section 6 and the operation-specific ordered boundary categories |

| Positive conformance; negative conformance | named vectors in the companion catalog; not unspecified future tests |
| Compatibility | `NO_DIVERGENCE`, except explicit `CLARIFICATION_ONLY` records in the matrix |

For pure helpers, trusted inputs/read-set/authority are **none**, time is **not applicable**,
and repeat invocation recomputes a result without persistence. For event-producing
operations, read-set additionally includes chain position and identity indexes; accepted
transition appends the named event and updates the corresponding replay projection.
Structural validation and candidate replay may reject before append. This is not a claim
that every failed compound operation appends zero events: first resource initialization
can precede a failed derivation/consume/release. Reservation plus derived-grant registration
itself is transactional in the accepted memory model.

## 3. Structural and semantic admission

`OP-EVT-001` admits the shapes in `schemas/agent-fabric/v0.1/control-event.schema.json` and
`validation.ts`. Required fields, closed object fields, finite numbers, integer boundaries,
nullable fields and closed enums belong to structural admission. Identifiers are nonempty;
goal objective/acceptance prose may be empty. `reservation = null` is a structurally valid
root-grant shape; it is not a general waiver of reservation semantics.

Cross-record uniqueness, duplicate resource entries, DAG validity, trusted evidence,
currentness, allocation conservation, exact lineage and digest correctness are semantic
obligations. Structurally valid fabricated events still require hardened replay. Conversely,
the JSON Schema operates on JSON data, not accessor/prototype behavior outside that model.

All 16 persisted event variants are enumerated by the operation catalog. No offer, worker
observation, planner output or digest can be substituted for a missing predecessor event.

## 4. Temporal and identity rules

Time values are finite, nonnegative epoch milliseconds where structurally specified;
P0a does not impose an integer constraint on every timestamp. Let `t` be the single pinned
clock observation for a synchronous public operation. Replay uses `event.occurredAt`,
not the replaying machine's wall clock. Equal consecutive event times are admitted.

| Object / boundary | Exact temporal requirement | Equality / rejection |
| --- | --- | --- |
| Owner authorization admission and use | `notBefore <= t < expiresAt`; `expiresAt > notBefore`; not revoked on use | before start rejects; at start accepts; interior accepts; at/after end rejects |
| Root grant registration | current owner authorization; grant interval nonempty and contained in authorization | registering a future grant is allowed; registration is not proof of current grant authority |
| Child registration | complete parent ancestry current at `t`; child interval nonempty and contained in parent | child may have a later `notBefore`; it cannot execute before that time |
| Grant use, including every ancestor | `notBefore <= t < expiresAt`; not revoked; derived reservation exists and is not released | lower equality admitted, upper equality rejected |
| Intent | `createdAt <= t` | equality admitted; future intent rejected |
| Offer | `expiresAt > t` | equality rejected; no authority is granted |
| Claim | positive lease duration; `committedAt = t`; `leaseExpiresAt = t + duration` | prior lease current iff `t < leaseExpiresAt`; replacement allowed at equality if other preconditions hold |
| Permit issuance | positive requested validity; `notBefore = t`; `expiresAt = min(t + validity, claim.leaseExpiresAt, grant.expiresAt)` | current claim and complete grant lineage required; nonempty interval |
| Permit use | `notBefore <= t < expiresAt`; current lease/fence/plan/lineage | before start or at/after end rejected; clipped permit does not bypass earlier ancestor expiry |
| Startup evidence | `permit.notBefore <= startedAt < permit.expiresAt` and `startedAt <= t` | evidence lower equality and equality to `t` admitted; current authority required at admission too |
| Worker result evidence | `attempt.startedAt <= reportedAt <= t` | lower and upper equality admitted; new commit also needs current permit/claim/plan/lineage |
| Outcome | `committedAt = t = event.occurredAt` | identical previously committed report retry is section 5's exception to fresh currentness checks |
| Uncertainty | `observedAt = t = event.occurredAt` | current permit window is not required; recorded identity is required |
| Event chain | `occurredAt >= predecessor.occurredAt` | equality admitted; regression rejected |

The clock pin prevents a single synchronous claim/permit/uncertainty/outcome operation
from inventing inconsistent times through multiple clock reads. It does not pin time
across asynchronous adapter execution.

Claim currentness reads active plan, terminal outcomes, current claim/lease and attempt
identity. A claim is committed before a grant is selected. Authorization revocation can
therefore coexist with a newly recorded scheduling claim, while subsequent permit issuance
fails. Requiring grant-at-claim would change accepted P0a, not clarify it.

Exact execution binding is:

```text
permit.intentId -> intent.planRevisionId -> revision.goalId -> goal.authorityInvocationId
permit.grantId  -> grant.rootAuthorizationId == goal.authorityInvocationId
authorization.goalIds includes goal.goalId
intent.rootExecutionId == revision.rootExecutionId == authorization.rootExecutionId == stream root
permit.claimId -> claim.intentId, attemptId, workerId, fencingToken
permit.planRevisionId == intent.planRevisionId
permit.effectiveRunSpecDigest == intent.effectiveRunSpecDigest
permit.workerId == claim.workerId == grant.subjectId
```

Permits also bind `permitId`, `grantId`, `notBefore` and `expiresAt`. Use requires canonical
equality to the recorded permit, not just a matching subset. A result report must bind
`attemptId`, `permitId`, `intentId`, `planRevisionId`, `effectiveRunSpecDigest` and
`fencingToken` to that lineage. Startup evidence binds attempt and observed spec digest.
The latest claim's generation is the previous fencing token plus one, starting at one.

## 5. Idempotency, identity and digests

Memory journal semantic identity is canonical content of exactly:

```text
{ eventId, rootExecutionId, idempotencyKey: key-or-null, payload }
```

`occurredAt` is excluded from that retry fingerprint, but included in event-chain hashing.
After structural validation and cloning, the journal checks a matching idempotency key
first, then event ID, before CAS. Equal fingerprint returns the prior cloned envelope,
even with a stale expected sequence or changed incoming timestamp. Different fingerprint
under an existing key throws `AF_CONFLICT`; under an existing event ID without matching
key throws `AF_DUPLICATE_ID`. A new event with stale CAS throws `AF_CONFLICT`.

The conductor derives event ID as `event:${idempotencyKey}`. Its operation keys are:

| Transition | Key |
| --- | --- |
| authorization / revocation | `owner-authorization:${authorizationId}` / `owner-authorization-revocation:${authorizationId}` |
| goal / grant / grant revocation | `goal:${goalId}` / `grant:${grantId}` / `grant-revocation:${grantId}` |
| ledger initialization | `resource-ledger:initialize` |
| consume / release | `resource-reservation-consume:${reservationId}` / `resource-reservation-release:${reservationId}` |
| delta / revision | `plan-delta:${deltaId}` / `plan-activation:${revisionId}` |
| intent / claim / permit | `dispatch-intent:${intentId}` / `claim:${intentId}:${fencingToken}` / `permit:${permitId}` |
| startup / uncertainty / outcome | `attempt-start:${attemptId}` / `attempt-uncertainty:${observationId}` / `attempt-outcome:${attemptId}` |

Method guards run before journal retry. There is no blanket promise that repeating any
conductor call returns success: authorization/goal/root registration still checks authority
and budgets; claim rejects reused attempts; permit rejects a second permit; plan activation
still checks CAS. Resource calls still synchronize the ledger and evaluate lifecycle.
If those guards pass, identical append keys use journal idempotency. A repeated consume
after a later release can reach an existing consume event; a first consume of a released
reservation has no such retry and is rejected by candidate replay.

Outcome retry computes the exact report digest and verifies identity before considering
current time. Same existing status and report digest return the original outcome; differing
content throws `AF_CONFLICT`. This records no new outcome and does not revive authority.

Persisted streams SHALL NOT contain duplicate event IDs or idempotency keys. Attempt IDs
are global across claims/intents in the stream, with at most one permit per attempt.
Startup report IDs, worker report IDs and outcome IDs are stream-global; individual
authorization/goal/grant/delta/revision/intent/claim/permit/observation identities cannot
introduce a second record of the same kind. Revocation facts are not ID reuse of the
registered authority object. These scopes do not assert global uniqueness across roots.

## 6. Rejection contract

Normative results distinguish: thrown `AgentFabricError`, `AuthorityResolution` with
`outcome = rejected` and reason codes, uncertainty (`status = unknown` in orchestration),
and a prior idempotent result. Human messages and diagnostic details are non-normative
unless a rule explicitly names a field. Tests assert codes/categories, not message prose.

| Code | Accepted boundary meaning |
| --- | --- |
| `AF_CANONICALIZATION_FAILED` | value outside canonical JSON profile; preserved through hardened replay |
| `AF_CONFLICT` | journal CAS/key conflict, active claim/outcome conflict, second permit, plan CAS, report mismatch |
| `AF_DUPLICATE_ID` | live reused attempt, event ID with changed fingerprint, duplicate raw ledger definition |
| `AF_GRANT_REJECTED` | missing/mismatched goal authority, untrusted authorization, inactive lineage, scope/subject/budget refusal at permit |
| `AF_INVALID_EVENT` | malformed structural event or semantic candidate/stream rejection, except existing protocol codes propagated from helpers |
| `AF_INVALID_PLAN` | live plan root/digest/DAG/delta/provenance rejection, intent missing node/goal |
| `AF_INVALID_STATE` | invalid temporal input outside permit/startup category, offer/lease, missing/substituted/unsynchronized ledger, pre-start outcome uncertainty |
| `AF_NOT_FOUND` | live lookup of missing revocation target, parent, intent, claim or reservation; missing started attempt after hardened lineage guard |
| `AF_PERMIT_REJECTED` | invalid permit duration, non-recorded permit, permit time window, startup attempt/spec/time mismatch |
| `AF_RESOURCE_EXHAUSTED` | live root allocation overcommit, raw ledger invalid amount/limit projection, missing materialized reservation |
| `AF_STALE_ATTEMPT` | superseded plan, inactive/expired claim, fencing or expired permit at new outcome commit |

The public hardened GoalContract guard runs before inner permit/dispatch/startup/outcome
logic. Missing grant/intent/goal lineage at that guard is `AF_GRANT_REJECTED`, even where
an inner implementation alone would report `AF_NOT_FOUND`. A missing claim at permit
issuance is checked first and reports `AF_NOT_FOUND`. Combined invalid inputs receive the
first applicable guard's code; this record does not reorder guards.

Candidate replay and offline replay can report different codes from an earlier live guard.
Examples: missing revocation target is live `AF_NOT_FOUND`, replay `AF_INVALID_EVENT`;
root allocation overflow is live `AF_RESOURCE_EXHAUSTED`, replay `AF_INVALID_EVENT`;
an authority helper's currentness rejection remains `AF_GRANT_REJECTED` through replay.
The hardened replay wrapper preserves **all existing** `AgentFabricError` codes and wraps
unexpected exceptions as `AF_INVALID_EVENT`. This is not an exception-normalization
guarantee for every public helper or arbitrary hostile JavaScript object.

### OP-RES-001 — initialize and hydrate canonical ledger

**Invariants:** I-RES-001/002/003/004; I-REPLAY-001.

| Facet | Rule |
| --- | --- |
| Inputs / trusted / read-set | trusted resource definitions via constructor seed, journal prefix; existing definitions, global/owner reserved/consumed totals and reservations |
| Preconditions | clone caller seed; fresh execution cannot import unexplained used seed; resume replays with same trusted definitions and reconstructs internal ledger; nonempty conflicting seed rejected |
| Transition / event | constructor hydration has no new event; first resource operation journals `resource_ledger_initialized` with sorted trusted definitions; initialized ledger must agree with replay |
| Authority / time | definitions are trust input, not worker telemetry; initialization uses pinned event time; no independent resource expiry clock |
| Retry / rejection | source object cannot replace internal ledger; passing different seed or mutated original seed, synchronization/seed conflict: `AF_INVALID_STATE`; raw ledger duplicate definition `AF_DUPLICATE_ID`, invalid limit `AF_INVALID_STATE` |
| Replay | definitions must match trust; missing trust, mismatched/duplicate initialization definitions: `AF_INVALID_EVENT`; empty mutable seed on restart cannot erase usage |

Resource projections are exact, separately per global resource and reservation owner:

| Semantics | Reserve | Consume active | Release active | Release consumed |
| --- | --- | --- | --- | --- |
| consumable | reserved += amount | reserved -= amount; consumed += amount | reserved -= amount | consumed unchanged |
| capacity | reserved += amount | reserved retained | reserved -= amount | reserved -= amount |
| counter | consumed += amount immediately | no further charge | no refund | no refund |

Initial reservation status is active if any request is non-counter, otherwise consumed.
Consume changes active to consumed; release changes status to released. Already consumed
consumption and already released release do not charge/refund again. Global and owner
projections use reserved + consumed against limits; all amounts are finite and positive.
Release can recover capacity but does not restore consumed/counter budgets or remove
historical child allocations from cumulative grant attenuation accounting.

## 8. Adoption boundary

The companion conformance matrix contains the per-rule obligation catalog, 35 invariant
rows, trust/direction classifications and all 15 planning gap dispositions. These are
candidate evidence, not retroactive P0a findings or self-issued independent acceptance.

Full S1.1 adoption still requires G-01 through G-14 of the adopted scope/gate, including
repository checks on the exact candidate SHA, an independent exact-SHA review with zero
unresolved BLOCKER/HIGH/MEDIUM, and an explicit merge/adoption event. A draft PR, local
green tests or this document's normative language cannot satisfy that event by themselves.
Any material extension or supersession discovered in review must be resolved explicitly;
it cannot be hidden in a prose edit or relabeled as clarification.
