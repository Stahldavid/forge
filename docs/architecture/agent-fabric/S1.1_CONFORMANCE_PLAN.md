# S1.1 — Normative Kernel Conformance Plan

**Record ID:** `AF-S1.1-CONFORMANCE-PLAN-2026-09-08`  
**Baseline:** `main@7a99ec5ceb2bdd51c83790fd84b23e534be52806`  
**Status:** `PLANNING_INPUT`  
**Purpose:** inventory existing P0a evidence, identify S1.1 conformance gaps, and define the evidence model for the future normative kernel  
**Normative status:** this plan is not itself a conformance verdict or normative protocol specification

## 1. Goal

This plan defines how S1.1 will prove that its normative rules faithfully describe the
accepted P0a deterministic protocol baseline and preserve the adopted S1.0 invariant set.

The plan deliberately distinguishes three questions:

1. **Is the behavior implemented?**
2. **Is there executable evidence for the specific invariant?**
3. **Has the behavior been stated as a precise normative rule?**

P0a acceptance answered the first question for the accepted baseline and provided strong
adversarial evidence overall. S1.1 must answer the third question and make the second
question traceable **per invariant**, not only per invariant family.

## 2. Evidence classifications

The current matrix uses the following conservative coverage labels.

### `STRONG`

The accepted implementation has a positive path plus one or more dedicated negative/
adversarial tests that materially exercise the invariant.

### `PARTIAL`

Meaningful implementation and regression evidence exists, but at least one material
boundary/dimension of the invariant lacks a dedicated conformance vector or the exact
normative interpretation still needs clarification.

### `STRUCTURAL`

The invariant is represented in types/schema/component separation, but there is no strong
behavioral conformance test for the invariant as a whole.

### `DIRECTION_ONLY`

The item is an adopted `FROZEN_DIRECTION` constraint for later slices and is not an
executable P0a conformance obligation.

### `ASSUMPTION`

The item is an explicit accepted trust assumption. It must be stated as an applicability
precondition rather than "proved" with a synthetic unit test.

### `GAP`

No sufficient implementation/evidence mapping currently exists. A testable `GAP` blocks
S1.1 adoption until resolved or reclassified through explicit governance.

These labels describe **current evidence shape**, not severity of defects. A `PARTIAL` row
does not imply P0a is unaccepted; it means S1.1 needs more precise conformance material than
was required for the prior vertical acceptance event.

## 7. Initial S1.1 gap register

The following gaps are planning findings, not P0a defect findings. They identify where the
normative phase needs additional precision/evidence.

### `S1.1-GAP-001` — attenuation dimension matrix

`I-AUTH-004` implementation checks all attenuation dimensions, but existing tests do not
independently mutate every dimension. S1.1 needs table-driven positive/negative vectors for
capabilities, sources, targets, effect classes, time, attempt budget, delegation depth, and
resource ceilings.

### `S1.1-GAP-002` — transitive expiry matrix

Revocation is strongly exercised; complete ancestor-expiry behavior is less directly
covered. Add root-authorization/root-grant/intermediate-child expiry vectors at permit,
startup and outcome boundaries.

### `S1.1-GAP-003` — claim currentness wording

`I-AUTH-007` names claim/permit/startup/outcome broadly, but a claim is committed before an
execution grant is selected. S1.1 must specify the exact currentness read-set at claim
(active plan, existing outcome/current claim/attempt identity) versus later grant-bound
boundaries. This should be a clarification, not an invented grant-at-claim requirement.

### `S1.1-GAP-004` — program/run-plan substitution vector

Add a dedicated negative conformance trace for `I-PLAN-001` rather than relying solely on
separate types and later plan-provenance tests.

### `S1.1-GAP-005` — materialization separation applicability

`I-PLAN-004` is structurally represented but deeper AgentSpec/HarnessSpec/ExecutionProfile
materialization is not implemented by P0a. The S1.1 matrix must separate structural P0a
obligations from later `DIRECTION_ONLY` semantics.

### `S1.1-GAP-006` — offer/claim/permit boundary proof

Add a dedicated trace demonstrating that an offer is non-authoritative and cannot be used
as a substitute for a claim/permit.

### `S1.1-GAP-007` — exact claim-lease boundary

Add `now < leaseExpiresAt`, `now == leaseExpiresAt`, and generation-rollover conformance
vectors for permit/outcome progression.

### `S1.1-GAP-008` — stale fenced worker trace

Add a two-generation test proving worker/claim generation N cannot commit after N+1 becomes
current.

### `S1.1-GAP-009` — restart matrix for all resource semantics

Exercise consumable/capacity/counter reserve/consume/release across restart and compare
future reservation decisions with the uninterrupted run.

### `S1.1-GAP-010` — full event-chain mutation matrix

Add sequence gap, reorder, predecessor identity, predecessor digest and event digest
single-fault vectors.

### `S1.1-GAP-011` — object-side canonicalization vectors

Add dedicated tests for accessors, symbols, non-enumerable properties and exotic object
prototypes to complement the strong array hardening corpus.

### `S1.1-GAP-012` — exact idempotency specification

Document/test the distinction between an API retry returning a prior event and a persisted
stream containing a duplicated event/idempotency identity.

### `S1.1-GAP-013` — exact error taxonomy

Create a rule-by-rule rejection table identifying when the accepted protocol throws
`AgentFabricError`, returns `AuthorityResolution.rejected`, returns uncertainty, or returns
an idempotent prior result. Human messages should remain non-normative unless needed.

### `S1.1-GAP-014` — systematic schema/runtime structural parity

Existing regressions cover important historical divergence cases, including empty goal text
and cross-item uniqueness being semantic rather than structural. S1.1 should define a
small parity vector set across every control payload class instead of relying on a few
historical examples.

### `S1.1-GAP-015` — unified temporal boundary table

Current code/tests implement many time rules, but S1.1 needs one normative table covering
authorization, grant, intent, claim, permit, startup, report and event timestamps, including
exact equality behavior.

## 9. Conformance vector strategy

### 9.1 Positive transition vectors

For every authoritative operation, establish the smallest valid prefix/input required for
success and assert:

- returned protocol object/result;
- exact appended event type and essential fields;
- resulting state projection;
- replay acceptance of the complete prefix.

### 9.2 Single-invariant negative mutations

Prefer one mutation per vector. Examples:

- wrong root execution;
- wrong goal authority ID;
- one expanded capability;
- one stale revision;
- one expired lease;
- one fencing mismatch;
- one permit-field substitution;
- one over-budget resource;
- one duplicate stream identity;
- one predecessor digest mutation.

This makes a failed test attributable to one normative obligation rather than an unrelated
precondition.

### 9.3 Live/replay differential vectors

For each persisted event family:

1. construct a valid live transition;
2. assert replay accepts the resulting prefix;
3. fabricate a semantically invalid but structurally valid counterpart;
4. rebuild the digest chain where needed;
5. assert replay rejects it under the same trust inputs.

### 9.4 Restart vectors

For stateful resource/claim/plan behavior, compare uninterrupted and restarted conductors
from the same authoritative prefix. Future decisions must match when trust inputs are the
same.

### 9.5 Canonicalization vectors

Maintain explicit byte/digest vectors for admitted values plus rejection vectors for values
outside the accepted JSON data model. S1.1 SHALL not generalize from JavaScript behavior to
cross-language JCS.

### 9.6 Structural schema/runtime vectors

For each payload variant, include representative:

- valid shape;
- missing required field;
- unknown field;
- wrong enum/type;
- nullability boundary;
- string/number/integer boundary where applicable.

Cross-record uniqueness/currentness belongs to semantic replay tests, not structural parity
unless the schema can and intentionally does express it.

## 10. Error/rejection conformance strategy

The final S1.1 matrix SHALL distinguish:

### Thrown protocol errors

Expected exact `AgentFabricError.code`; optional details constraints if programmatically
relevant.

### Structured authority rejection

Expected `AuthorityResolution.outcome = rejected` plus stable reason category.

### Non-authoritative uncertainty

Expected `status = unknown` plus persisted `AttemptUncertaintyObservation`, with no terminal
outcome.

### Idempotent retry

Expected same previously committed semantic event/result and no second persisted event.

Tests SHALL NOT assert exact human-readable messages unless S1.1 explicitly declares the
message normative.

## 11. Temporal conformance strategy

The final specification SHALL include a table with at least these boundary points for each
applicable time-bounded object:

```text
now < notBefore
now == notBefore
notBefore < now < expiresAt
now == expiresAt
now > expiresAt
```

For leases, replace `notBefore` with commit/current-claim semantics and include:

```text
now < leaseExpiresAt
now == leaseExpiresAt
now > leaseExpiresAt
```

For evidence timestamps, distinguish the evidence timestamp from the authoritative
transition `now`.

A synchronous authoritative transition whose invariant requires timestamp equality SHALL
use one authoritative clock observation; the conformance vector SHALL use an advancing
clock to detect accidental multiple reads.

## 12. Conformance and S1.3 boundary

S1.1 SHALL define precise obligations and may add focused regression tests/vectors needed to
remove `BLOCKING_GAP` entries.

S1.1 does **not** need to implement:

- a generic protocol conformance runner;
- formal state-machine/model-checking infrastructure;
- proof artifact signing;
- cross-language conformance harnesses;
- production evidence retention services.

Those are candidates for later Proof & Conformance work. S1.1 must leave enough stable rule
IDs and vector definitions for such tooling to consume without reinterpreting prose.
