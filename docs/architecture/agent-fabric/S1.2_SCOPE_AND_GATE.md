# S1.2 — Reference Implementation Design: Scope and Gate

**Record ID:** `AF-S1.2-SCOPE-2026-09-10`

**Status:** `PLANNING_PROPOSAL`

**Baseline:** `main@4b796f49c480d782ec7e069f8eb5f7eae841876a`

**Authority:** proposed documentation/design scope; no new runtime or protocol authority.

## 1. Proposed objective and provenance

S1.1 specifies what the accepted P0a protocol does. This proposal defines the next slice
as **S1.2 — Reference Implementation Design**: make it possible to locate, inspect and
maintain the implementation of every adopted rule without guessing which component owns
authority, mutable state or a failure boundary.

The S1.2 name and objective are proposed here. The inspected governance baseline contains
no earlier formal S1.2 definition; its S1.1 conformance plan mentions later S1.3 Proof &
Conformance work but does not define the intervening slice. This proposal does not claim
to recover an already approved roadmap or silently assign new implementation work to it.

The result will be an implementation design **of the accepted reference behavior**, with
source and evidence traceability. It is not a replacement normative kernel, a speculative
production design, or permission to refactor the implementation. Optional improvement
ideas must remain explicitly non-operative and separately scoped.

## 2. Frozen inputs and precedence

Consume the adopted S1.0B1/B2 freezes, P0a acceptance record, S1.1 scope/conformance plan,
kernel/matrix and [S1.1 adoption record](./S1.1_ADOPTION_RECORD.md). The README's precedence
and supersession rules continue to apply. P0a accepted behavior and schema/hardened replay
cannot be overridden by a later design diagram or a cleaner-looking abstraction.

The complete design must identify its exact source baseline. If relevant code or normative
inputs move before review, each affected mapping must be reevaluated and the new baseline
recorded. A purely historical acceptance record continues to refer to its original SHA.

## 3. In-scope questions

The complete design must answer, with file/symbol references and adopted OP/I links:

1. Which public entrypoint admits each operation, and which internal components implement
   it? Which exported helpers lack the complete conductor's guarantees?
2. Who owns each control-state projection and mutable resource ledger? Where are caller
   inputs cloned, frozen, compared, replayed or rejected?
3. Where are trusted verifier/definitions/clock/journal inputs introduced? Which inputs
   remain worker evidence or scheduling proposals rather than authority?
4. In what order do live guards, candidate replay, journal idempotency/CAS and publication
   execute? Which boundaries return prior results, rejection, uncertainty or errors?
5. How do constructor hydration, resource transactions and replay interact? What can have
   been journaled when a compound call fails, and what rollback is actually provided?
6. How do scheduling, fenced attempts, startup, late evidence and outcomes cross component
   boundaries without collapsing their different meanings?
7. Which responsibilities are only structural or frozen direction, and therefore have no
   accepted runtime implementation or production guarantee to map?

Every answer describes observed source behavior or explicitly labels an inference. An
unresolved answer about an in-scope responsibility is a design gap, not automatic evidence
of a P0a defect. A concrete code/protocol defect discovered during mapping still receives
its own severity and decision disposition; it must not be hidden as mere missing prose.

## 5. Non-objectives and change boundary

Both the scope PR and complete-design PR are documentary. They must not alter source,
schema, tests, package exports, dependencies, workflows, timeouts or generated artifacts.
Reading existing tests and running applicable verification is allowed; changing tests or
writing a new test runner is not part of this slice.

In particular, this slice does not:

- add/refactor a service, public API, authority guard, journal implementation or reducer;
- strengthen or weaken an adopted OP/I rule, reorder guards or normalize error codes;
- implement P0b, a real provider adapter, consequential effects or reconciliation;
- design/adopt production storage transactions, outbox, failover or recovery epochs;
- implement adaptive routing, a full harness compiler, isolation enforcement, persistent
  memory, plugin promotion, evolution or production readiness/security certification;
- implement S1.3's generic runner, formal models, proof signing, evidence retention or
  cross-language conformance/JCS.

Any runtime/test/schema repair found to be necessary is a separately authorized change,
with its own scope, compatibility evidence and exact-SHA review. If the design depends on
such a change, it cannot be called a faithful baseline design and adopted while that
dependency remains pending. If an optional idea is deferred, no in-scope obligation may
depend on it being implemented.

This is a decision to document and inspect boundaries, not a production design acceptance
for capabilities marked `FROZEN_DIRECTION` or `DEFERRED` in S1.0.

## 6. Evidence and decision model

Use `OBSERVED` for a referenced source/event/test fact, `INFERRED` for a supported
interpretation that needs review, and `PROPOSED` for non-operative design ideas. Preserve
S1.1's coverage classes, including `STRUCTURAL_ONLY`, `ASSUMPTION` and `DIRECTION_ONLY`;
S1.2 must not relabel them as behavioral proof through documentation alone.

Map each discrepancy to the existing decision classes:

| Class | Required treatment |
| --- | --- |
| `NO_DIVERGENCE` | direct source mapping, with evidence |
| `CLARIFICATION_ONLY` | explain why wording changes no accepted semantics; cite OP/I and source |
| `COMPATIBLE_IMPLEMENTATION_REFINEMENT` | optional implementation proposal only; separate code scope/review required; cannot be counted as implemented |
| `EXTENSION_REQUIRED` | explicit separate extension decision and acceptance required; a dependent in-scope design item blocks adoption |
| `SUPERSESSION_REQUIRED` | name the superseded invariant/rule and required compatibility decision; a dependent item blocks adoption |
| `DEFERRED_NON_APPLICABLE` | preserve exclusion; explain why no required baseline mapping depends on it |

No `UNCLASSIFIED` discrepancy is allowed at adoption. Missing evidence for an applicable
design obligation is `BLOCKING_GAP`, not an assumption or an optional future idea. The
independent review determines whether a proposed disposition is adequate.
