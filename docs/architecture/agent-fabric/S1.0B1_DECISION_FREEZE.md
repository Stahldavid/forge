# S1.0B1 — Agent Fabric Decision Freeze

**Freeze ID:** `AF-S1.0B1-2026-09-08`  
**Baseline implementation:** `bfd2639579e650d4ad38ec1a81dbd55a5d68865e`  
**Baseline on main:** `8972496f09727456b8b9f3ceafc386beab5f39d0`  
**Scope:** architecture decisions and protocol invariants established through the P0a deterministic vertical  
**Adoption state:** proposed formal record; becomes adopted when this governance package is merged to `main`

## 1. Purpose

S1.0B1 freezes the decisions that future Agent Fabric work must treat as architecture
constraints rather than rediscovering them opportunistically inside later implementations.

The freeze exists to prevent four failure modes:

1. a later runtime feature accidentally manufacturing authority that the control plane did
   not grant;
2. nondeterministic work being confused with deterministic replay/control state;
3. terminology drifting so that offer, claim, permit, execution, report, and authoritative
   outcome become interchangeable;
4. implementation details of the P0a TypeScript reference becoming confused with the
   eventual cross-language normative protocol.

This record therefore freezes **semantics and boundaries**, not every current line of code.
A later implementation may replace internal mechanisms while preserving the same frozen
invariants, or it may explicitly supersede a decision through a new governance record.

## 2. Baseline classes

Every item below is classified as one of:

- **ACCEPTED_P0A** — implemented, adversarially reviewed, and accepted in the merged P0a
  baseline;
- **FROZEN_DIRECTION** — architecture direction accepted as the target decomposition or
  semantic rule, but not fully implemented by P0a;
- **DEFERRED** — intentionally not accepted as implemented behavior.

The classification is part of the freeze. A `FROZEN_DIRECTION` item must not be presented
as already implemented merely because its name appears here.

## 3. Frozen macroarchitecture

### D-001 — Agent Fabric is a governed meta-runtime, not a single agent

**Class:** `FROZEN_DIRECTION`

Agent Fabric coordinates dynamically materialized agents/workflows while keeping control,
authority, evidence, and consequential effects separately governed. A cognitive worker,
model, strategy, or planner is not itself the trusted authority plane.

### D-002 — Top-level component decomposition

**Class:** `FROZEN_DIRECTION`

The target architecture is decomposed into these responsibility domains:

1. **Forge Intelligence** — repository/architecture graphs, grounding/context resolution,
   dataflow classification, DepLens-like analysis, and governed memory compilation;
2. **Adaptive Harness Runtime** — materialization of `AgentSpec`, `HarnessSpec`, execution
   profiles, transparent workflows, and sandboxed opaque activities;
3. **Forge Conductor** — goals, plans/revisions, dispatch, claims, leases/fencing,
   authority-aware permits, resource budgets, journal/control state, child lifecycle, and
   recovery coordination;
4. **Forge Assurance** — source observations/assessments, evidence artifacts,
   verification/obligations, independence disclosure, domain acceptance policy, and
   acceptance records;
5. **Consequential Effect Broker** — target resolution, preparation, authorization grants,
   effect attempts/receipts/readback/reconciliation;
6. **Evolution Registry** — improvement candidates, extensions, governance profiles,
   evals, promotion/canary/rollback/revocation;
7. **Trusted Privilege Domain** — the deliberately small trusted computing/control base that
   authenticates and validates authority-changing operations.

P0a implements only a narrow deterministic control-plane vertical, primarily in the
Conductor/authority/replay area.

### D-003 — AHCP is a protocol, not a standalone service

**Class:** `FROZEN_DIRECTION`

Adaptive Harness–Conductor Protocol (AHCP) is the contract between adaptive harness
execution/materialization and the governed conductor. It must not be treated as an
independent service whose existence itself grants authority.

## 4. Frozen core vocabulary

The following names have stable meanings for subsequent slices.

### `OwnerAuthorization`

An authenticated root authority envelope supplied by an authorized principal. It bounds:
root execution, goals, subjects, capabilities, sources, targets, effect classes, validity
window, attempt budget, delegation depth, and resource ceilings.

It is **not** equivalent to a user request string, model instruction, or planner intent.

### `OwnerAuthorizationVerification` / `OwnerAuthorizationVerifier`

Evidence and trusted verifier interface proving that the exact content of an
`OwnerAuthorization` was admitted through the trusted authority boundary. Replay requires
deterministic/offline verification of recorded evidence.

### `GoalContract`

The accepted goal definition for a root execution: objectives, non-objectives, acceptance
criteria, effect boundaries, source boundary, and the exact `authorityInvocationId` from
which execution authority for the goal originates.

### `WorkflowProgramVersion`

A workflow/program definition independent of one particular execution instance.

### `RunPlanRevision`

An instance-local plan revision for a specific root execution and goal. A revision has
explicit parentage and, after the initial revision, an exact originating `PlanDelta`.

### `PlanDelta`

A proposed/registered set of explicit plan mutations between revisions. A `PlanDelta`
proposes structure; it does not grant authority.

### `AgentSpec`

A description of an agent role/objective/instructions/output contract/stop conditions.
It describes work, not authority.

### `HarnessSpec`

A description of runtime harness composition: prompt layers, tools, plugins, memory mode,
and delegation mode. It describes materialization, not authority.

### `ExecutionProfile`

Isolation/network/filesystem/durability/wall-clock constraints for execution.

### `EffectiveRunSpec`

The content-bound, materialized run specification for a node. Its digest identifies the
exact representation the worker is expected to execute. Effective-run-spec identity is
separate from dynamic authority/currentness.

### `ExecutionGrant`

A capability/source/target/effect/time/budget authority object rooted in one exact
`OwnerAuthorization`. Child grants are attenuated delegations and never authority
amplifications.

### `ResourceLedger`

Authoritative accounting of resource definitions, reservations, consumption, and
per-owner totals. The conductor's canonical resource state is reconstructed from trusted
resource definitions plus authoritative journal history; caller-owned mutable objects are
not authority.

### `ResourceReservation`

A concrete reservation supporting delegated authority/resource use. A derived grant whose
required reservation is released is no longer current for future authoritative execution.

### `DispatchIntent`

A durable statement that the conductor intends a specific task-node/effective-spec/target
operation under a plan revision. Intent is not a worker permit.

### `DispatchOffer`

A non-authoritative scheduling advertisement. Receiving an offer creates no right to
execute or commit.

### `SchedulingClaim`

The authoritative scheduling ownership record for an attempt during a lease window. It
binds intent, worker, attempt, lease and fencing generation. A claim is stronger than an
offer but still not an execution permit.

### Lease

The time-bounded currentness of a scheduling claim. Expired claims do not retain execution
or commit authority.

### Fencing token

A monotonically ordered generation used to reject stale workers/claims. Physical stale
workers may exist, but stale generations must not commit authoritative state.

### `AttemptExecutionPermit`

The explicit execution authority token for one attempt. It binds permit, intent, claim,
attempt, worker, plan revision, `EffectiveRunSpec` digest, grant, fencing token, and time
window.

### `ExecutorStartupReport`

Evidence that an executor claims to have started a permitted attempt and observed a
specific run-spec digest. It is evidence, not self-created authority.

### `WorkerResultReport`

A worker's content-bound result/evidence report. It is non-authoritative input until the
trusted control path validates it against current permit/claim/grant/plan/fencing
lineage.

### `AttemptUncertaintyObservation`

Evidence that startup or outcome may have happened but cannot be admitted as an
authoritative terminal result under current authority. Uncertainty is deliberately
non-terminal.

### `AuthoritativeOutcomeCommit`

The trusted control-plane record that a currently authorized attempt has a terminal
`succeeded` or `failed` outcome, with provenance bound to the worker report and exact
execution lineage.

### `ControlEventEnvelope`

The authoritative event representation carrying root execution, sequence, predecessor
identity/digest, event digest, authoritative timestamp, optional idempotency identity, and
one closed control payload variant.

### Replay

Deterministic reconstruction and semantic validation of accepted control state from the
trusted journal prefix. Replay must not rerun nondeterministic cognitive work.

## 5. Frozen authority invariants

### I-AUTH-001 — Strategy cannot manufacture authority

**Class:** `ACCEPTED_P0A` for the implemented authority path; broader architecture rule is
frozen for later slices.

Planner/model/strategy output may propose goals, plans, deltas, harnesses, or actions, but
only trusted authority-control transitions may create grants/claims/permits/authoritative
outcomes.

### I-AUTH-002 — Root authority is verified and content-bound

A root grant must trace to a registered `OwnerAuthorization` whose exact canonical content
has trusted verification evidence. Hashing alone is not owner authentication.

### I-AUTH-003 — Goal authority binding is exact

For an execution permit, the grant's `rootAuthorizationId` must equal the active
`GoalContract.authorityInvocationId`; the authorization must include the goal; and the
authorization, plan revision, dispatch intent, and permit lineage must refer to the same
root execution.

### I-AUTH-004 — Delegation is monotonic attenuation

A child grant may narrow but may not expand capabilities, sources, targets, effect classes,
time window, attempt budget, delegation depth, or resource ceilings relative to its
parent/root authority.

### I-AUTH-005 — Revocation and expiry are transitive

A grant is current only if its complete ancestry and root authorization are current. An
expired/revoked ancestor invalidates descendant execution authority.

### I-AUTH-006 — Reservation currentness participates in authority

A derived grant requiring a resource reservation is not current if the reservation is
missing or released.

### I-AUTH-007 — Authority currentness is checked at consequential control boundaries

Claim/permit/startup/outcome transitions may not rely solely on historical validity. The
relevant authority/plan/lease/fencing lineage must still be current at the transition that
creates authoritative control state.

## 6. Frozen plan and materialization invariants

### I-PLAN-001 — Workflow program identity and run-plan identity are distinct

`WorkflowProgramVersion` is a reusable program definition. `RunPlanRevision` is local to a
root execution and preserves root execution, goal, and program identity.

### I-PLAN-002 — Plan evolution is explicit

A non-initial plan revision must be exactly derivable from a registered `PlanDelta` with
valid base/parent/next-revision lineage. The planner may propose a delta; the conductor
validates and activates it.

### I-PLAN-003 — Effective run content identity is not authority

A correct `EffectiveRunSpec` digest proves what representation was selected; it does not
prove the holder is still authorized to execute or commit it.

### I-PLAN-004 — Agent, harness, profile, and effective materialization remain separate

`AgentSpec`, `HarnessSpec`, `ExecutionProfile`, and `EffectiveRunSpec` must not collapse
into one ambiguous mutable object. Later routing/harness work may enrich these contracts
but must preserve the separation of role/instructions, harness composition, execution
constraints, and materialized run identity.

## 7. Frozen scheduling/execution invariants

### I-EXEC-001 — Offer, claim, permit, physical execution, and authoritative outcome are distinct

The architecture explicitly rejects the equivalence:

`offer == claim == permit == execution == committed outcome`.

Each boundary has different semantics and authority.

### I-EXEC-002 — Attempt identity is stream-global

An `attemptId` is not reusable for another claim/intent. One attempt has one claim lineage
and at most one execution permit.

### I-EXEC-003 — Claim lease is time-bounded

An expired claim may not authorize a fresh permit/startup/outcome merely because the claim
record still exists.

### I-EXEC-004 — Fencing rejects stale generations

A stale worker or duplicate worker may physically continue to exist, but only the current
fenced generation may commit authoritative startup/outcome state.

### I-EXEC-005 — Permit binding is exact

A permit binds at least: permit ID, intent ID, claim ID, attempt ID, worker ID, plan
revision ID, effective-run-spec digest, grant ID, fencing token, and validity window. A
permit from another lineage is not substitutable.

### I-EXEC-006 — Worker report is evidence, not commit

A validly shaped `WorkerResultReport` is not an authoritative result by itself. Commit
requires trusted revalidation of the exact permit/intent/plan/spec/fence lineage and
current authority.

### I-EXEC-007 — Ambiguous/late evidence becomes uncertainty, not invented terminal state

If a positive startup/outcome report arrives after authority becomes stale, or execution
state cannot be admitted with certainty, the control plane may retain a non-terminal
`AttemptUncertaintyObservation`; it must not fabricate success/failure merely to make the
state machine terminal.

### I-EXEC-008 — Uncertainty does not by itself block retry

The existence of uncertainty evidence is not an authoritative terminal outcome. Retry is
permitted if a new current claim/permit can be legitimately issued under remaining
budgets/authority.

### I-EXEC-009 — P0a terminal outcome domain is closed

P0a authoritative terminal outcomes are only `succeeded | failed`. `unknown` is evidence
or observation state, not a terminal committed outcome.

## 8. Frozen resource invariants

### I-RES-001 — Resource state is authority-relevant state

Resource budgets are not advisory telemetry. Resource definitions, reservations,
consumption, release, and owner/global totals participate in whether delegated authority
may be created/used.

### I-RES-002 — Global and owner accounting must not overcommit

Replay and live transitions must reject unknown resources, duplicate/invalid requests,
invalid reservation transitions, and aggregate resource overcommit.

### I-RES-003 — Canonical resource state comes from journal + trusted definitions

On resume, accumulated resource state is reconstructed from the authoritative journal and
trusted definitions. An empty mutable caller seed cannot erase prior usage; an external
mutation cannot change conductor authority; conflicting non-empty seed state fails closed.

### I-RES-004 — Reservation lifecycle is replayable

Reserve/consume/release effects on the control ledger must have deterministic replay
semantics so restart cannot restore released capacity/authority incorrectly or forget
consumption.

## 9. Frozen journal, identity, and replay invariants

### I-REPLAY-001 — Accepted control decisions are persistable/replayable; cognition is not replayed

Replay reconstructs control state from accepted event data. It must not recall an LLM,
planner, remote inference provider, or other nondeterministic activity to rediscover an
accepted control decision.

### I-REPLAY-002 — Live authoritative transitions must be replay-valid before append

A public authoritative transition must not report success and append a prefix that the
same accepted replay semantics later reject. Candidate authoritative events are validated
against the candidate prefix before append.

### I-REPLAY-003 — Root execution streams do not mix

A control stream is scoped to one root execution. Events from another root are not
admissible into the same replay state.

### I-REPLAY-004 — Event-chain integrity is explicit

Sequence, predecessor event ID, predecessor digest, event digest, and authoritative event
time are validated. Reordering, gaps, predecessor tampering, digest tampering, or invalid
time monotonicity fail closed.

### I-REPLAY-005 — Stream identities are unique where identity semantics require it

At minimum P0a enforces uniqueness/currentness for event/idempotency/result/attempt/permit
identities relevant to avoiding replay/live confusion. Reusing an identity with different
content must not create a second authoritative meaning.

### I-REPLAY-006 — Recorded report digest is recomputed from persisted fields

Replay reconstructs the canonical `WorkerResultReport` representation from persisted
outcome fields and recomputes its digest. A recorded digest cannot bless different report
content.

### I-REPLAY-007 — Malformed input fails in the protocol error domain

Malformed control input is rejected as `AgentFabricError(AF_INVALID_EVENT)` rather than
leaking implementation-specific exceptions such as `TypeError` as protocol semantics.

## 10. Frozen canonicalization decisions

### I-CANON-001 — Digests bind the exact admitted representation

A digest used for authority/evidence/provenance must be computed from a deterministic
canonical representation of the exact admitted data, not from a transformation that can
silently discard semantically distinct properties.

### I-CANON-002 — P0a canonical profile is a JavaScript/TypeScript reference profile

P0a uses `forge-canonical-json/v0.1` with SHA-256. It is not the final cross-language
standard and must not be described as RFC 8785/JCS conformance.

### I-CANON-003 — Canonicalization is over a strict JSON data model

Admitted objects are plain or null-prototype data objects with own enumerable data
properties. Own `__proto__` is ordinary data and participates in canonical bytes.
Accessors, symbol properties, exotic object prototypes, sparse arrays, array extra/symbol
properties, and arrays with non-`Array.prototype` prototypes fail closed.

### I-CANON-004 — Canonicalization does not dispatch methods on untrusted input

Array normalization reads validated own index descriptors rather than invoking an inherited
or overridden `map`/iterator method. Canonical output therefore cannot be controlled by an
input prototype method.

## 11. Frozen trust boundaries

### T-001 — Journal-origin trust is separate from hash-chain integrity

**Class:** `ACCEPTED_P0A` assumption.

The event digest/predecessor chain proves internal integrity of the supplied prefix; it is
not a signature proving storage origin. P0a assumes the authoritative replay prefix comes
from the trusted journal/storage boundary.

Production durable journal authentication is deferred.

### T-002 — Owner authorization trust enters through the verifier boundary

The trusted `OwnerAuthorizationVerifier` decides whether exact owner-authorization content
is admissible and whether recorded verification evidence remains valid during replay.

### T-003 — Resource definitions are replay trust input

Resource definitions/limits are supplied through the replay trust context and are not
magically inferred from worker claims.

### T-004 — Hashes provide content binding, not semantic authorization

A correct digest does not itself grant execution authority. Authority is derived from
verified owner authorization + current grant/plan/claim/permit lineage.

### T-005 — The trusted privilege domain should remain small

**Class:** `FROZEN_DIRECTION`.

Semantic validators that can create/activate/revoke authority or admit consequential
control state belong in the trusted path. Cognitive code, plugins, arbitrary model output,
and strategy logic should remain outside that trusted privilege domain wherever possible.

## 12. Frozen evidence/epistemic principles for later slices

These are `FROZEN_DIRECTION` and are not claimed as fully implemented by P0a:

- sender identity, content author, and instructional authority are separate dimensions;
- raw/captured `SourceObservation` is distinct from epistemic `SourceAssessment`;
- chain-of-thought is not required as evidence;
- evidence artifacts should bind exact representations/digests where provenance matters;
- verification status should use explicit states such as `pass`, `fail`, `not_supported`,
  `not_applicable`, `blocked`, and `inconclusive` rather than forcing binary success;
- acceptance is a governed decision with explicit applicability, not an informal statement
  that tests once passed.

## 13. Read-only semantic rule

### D-READ-001 — Read-only forbids target mutation, not internal control persistence

**Class:** `FROZEN_DIRECTION` for P0b and later.

A read-only agent/activity may still append internal journal/evidence/projection records
needed to govern the run. `read-only` means it may not mutate the governed external target
or cross into consequential effect classes. Internal trusted control-state persistence is
not itself a prohibited target effect.

## 14. Explicitly deferred / not accepted as implemented

The following are **DEFERRED** and must require separate design, implementation, evidence,
and acceptance:

1. P0b nondeterministic real model/agent adapter vertical;
2. production persistent/PGlite Agent Fabric journal;
3. transactional production outbox/persistence coupling;
4. real consequential-effect broker;
5. requested → resolved → authorized → materialized → observed → reconciled effect chain;
6. external effect receipts/readback/reconciliation;
7. integrity-unknown recovery and authority epochs;
8. production recovery/checkpoint semantics;
9. adaptive model routing and full harness compilation;
10. dynamic plugin installation/promotion;
11. persistent governed memory;
12. Evolution Registry promotion/canary/rollback/revocation;
13. production deployment/readiness claims;
14. production security claims beyond the reviewed experimental P0a surface;
15. final cross-language canonicalization profile/test vectors;
16. completion of Forge Assurance beyond the evidence/trust principles frozen above.

## 15. Decision-change rule

Future work must treat the identifiers in this record as stable references. If a later
slice discovers that an invariant is wrong or insufficient, the correct action is not to
quietly weaken it. The change must:

1. identify the invariant/decision ID;
2. classify the change as clarification, extension, or supersession;
3. provide the exploit/requirement motivating the change;
4. define migration/backward-compatibility impact;
5. add negative/positive conformance evidence;
6. identify the new exact accepted commit;
7. update the acceptance applicability record.

## 16. S1.0B1 exit condition

S1.0B1 is formally closed when this record is merged to `main` and therefore becomes the
repository-native authoritative decision freeze for subsequent Agent Fabric slices.

Closing S1.0B1 does **not** by itself open or accept S1.1/S1.5/P0b; it only provides the
stable decision input those slices must consume.
