# S1.1 — Normative Kernel Scope and Acceptance Gate

**Record ID:** `AF-S1.1-SCOPE-PLAN-2026-09-08`  
**Baseline:** `main@7a99ec5ceb2bdd51c83790fd84b23e534be52806`  
**Consumes:** `S1.0B1_DECISION_FREEZE.md`, `S1.0B2_EVIDENCE_FREEZE.md`, `P0A_ACCEPTANCE_RECORD.md`  
**Status:** `PLANNING_INPUT`  
**Normative status:** this document scopes S1.1; it is **not** the S1.1 Normative Kernel itself  
**P0b authorization:** not granted

## 1. Purpose

S1.1 converts the adopted S1.0 architecture freeze into a precise normative protocol
kernel for the accepted deterministic Agent Fabric control-plane semantics.

The problem S1.1 solves is narrower than "design Agent Fabric" and broader than "document
the current TypeScript methods". The S1.0 freeze already established the architecture
constraints. P0a already proved one executable reference vertical. S1.1 must now express
the accepted semantics so that:

1. an implementation can determine exactly what a conforming transition must accept,
   produce, reject, and persist;
2. a reviewer can distinguish protocol requirements from implementation accidents;
3. live behavior and replay behavior can be compared against the same rules;
4. later slices can extend the kernel without silently redefining the accepted P0a
   authority model;
5. conformance evidence can be attached to stable rule identifiers rather than informal
   prose.

S1.1 is therefore a **semantic specification phase**. It consumes S1.0; it does not reopen
S1.0 by default.

## 2. Source authority and precedence

S1.1 SHALL consume the adopted governance package using the precedence already adopted by
`docs/architecture/agent-fabric/README.md`.

For the accepted P0a semantics, the order remains:

1. accepted executable behavior in the accepted P0a tree included by `main`;
2. machine-readable schema and hardened validation/replay behavior;
3. `P0A_ACCEPTANCE_RECORD.md`;
4. `S1.0B1_DECISION_FREEZE.md`;
5. `S1.0B2_EVIDENCE_FREEZE.md`;
6. `docs/agent-fabric.md`;
7. older notes, handoffs, experiments, or conversation history.

S1.1 MAY clarify ambiguity between these sources only if the clarification preserves the
accepted behavior. If resolving an ambiguity would materially change a frozen invariant,
trust boundary, event meaning, public authority path, canonical representation, or replay
semantics, S1.1 MUST stop and create an explicit clarification/extension/supersession
record under the S1.0 decision-change rule.

## 3. Normative language

The eventual `S1.1_NORMATIVE_KERNEL.md` SHALL use the key words **MUST**, **MUST NOT**,
**REQUIRED**, **SHALL**, **SHALL NOT**, **SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**,
and **OPTIONAL** in their standards sense only when written in uppercase.

Normative text SHALL be distinguishable from:

- rationale;
- examples;
- implementation notes;
- accepted P0a evidence;
- future/deferred architecture direction.

A statement SHALL NOT become normative merely because the current TypeScript
implementation happens to behave that way.

## 4. S1.1 objective

S1.1 SHALL define the normative behavior of the accepted deterministic Agent Fabric
kernel, including:

- data and identity semantics needed by authoritative control state;
- trusted inputs and trust assumptions;
- preconditions and authority/currentness checks;
- deterministic state-transition semantics;
- event production and event-envelope requirements;
- idempotency and duplicate handling;
- temporal boundaries;
- canonicalization and digest binding;
- structural versus semantic validation boundaries;
- protocol rejection/error outcomes;
- live/replay equivalence obligations;
- conformance obligations mapped to each adopted invariant.

S1.1 SHALL preserve the distinction between:

- `ACCEPTED_P0A` behavior that is executable and testable today;
- `FROZEN_DIRECTION` constraints that later slices must respect but P0a is not required to
  fully implement;
- `DEFERRED` capabilities that remain outside S1.1 acceptance.

## 5. Explicit non-objectives

S1.1 SHALL NOT, merely by being specified or adopted:

1. implement or authorize P0b;
2. introduce a real nondeterministic model/provider adapter;
3. claim production journal/storage durability;
4. define PGlite production transactionality;
5. define production transactional-outbox guarantees;
6. authorize or implement consequential external effects;
7. define resolved-target/effect-receipt/readback/reconciliation semantics;
8. define integrity-unknown recovery or authority epochs;
9. define production checkpoint/failover behavior;
10. implement adaptive routing or a full Adaptive Harness Compiler;
11. authorize dynamic plugin installation/promotion;
12. implement persistent governed memory;
13. implement the Evolution Registry;
14. complete Forge Assurance beyond the adopted evidence/trust principles;
15. make production deployment/security-readiness claims;
16. claim RFC 8785/JCS or other cross-language canonicalization conformance;
17. replace the existing S1.0 decision freeze without an explicit superseding decision.

S1.1 MAY mention those domains only to state a boundary, reserved interface, or
non-applicability condition inherited from S1.0.

## 6. Required S1.1 deliverables

The full S1.1 adoption PR SHALL contain, at minimum, the following repository-native
artifacts.

### 6.1 `S1.1_NORMATIVE_KERNEL.md`

The normative protocol text. It SHALL define all operations and cross-cutting semantics in
this scope.

### 6.2 `S1.1_CONFORMANCE_MATRIX.md`

A rule/invariant/evidence matrix. Every adopted `I-*` invariant SHALL have an explicit row.
Every normative operation SHALL map to its implementation and positive/negative evidence
or to an explicitly classified coverage gap.

### 6.3 Conformance obligation catalog

The S1.1 PR SHALL provide a stable obligation catalog, either as a dedicated section of the
matrix or as a small machine-readable artifact. Each obligation SHALL have a stable ID and
at least:

- normative rule reference;
- invariant references;
- applicability class;
- evidence type;
- implementation reference;
- positive conformance reference where testable;
- negative conformance reference where testable;
- current status.

A generic conformance runner or formal-model framework is **not** required by S1.1. Those
belong to later proof/conformance work. S1.1 defines what must be proved, not the final
universal mechanism for proving it.

### 6.4 Divergence register

The S1.1 PR SHALL contain an explicit register of every discovered mismatch among:

- frozen invariant;
- accepted implementation;
- schema;
- runtime validator;
- replay semantics;
- proposed normative wording.

Every entry SHALL be resolved as one of:

- `NO_DIVERGENCE`;
- `CLARIFICATION_ONLY`;
- `COMPATIBLE_IMPLEMENTATION_REFINEMENT`;
- `EXTENSION_REQUIRED`;
- `SUPERSESSION_REQUIRED`;
- `DEFERRED_NON_APPLICABLE`.

No semantic divergence may remain silently unresolved at S1.1 acceptance.

## 7. Rule granularity

S1.1 SHALL not specify only broad categories such as "authority is checked" or "replay is
deterministic". Normative rules SHALL be operation-shaped and independently traceable.

Each operation rule SHALL specify all applicable fields below.

1. **Rule ID** — stable S1.1 identifier.
2. **Invariant references** — exact S1.0 IDs consumed.
3. **Inputs** — caller-supplied data.
4. **Trusted inputs** — verifier/resource/journal trust inputs not supplied by an untrusted
   worker.
5. **State read-set** — authoritative state required to decide the transition.
6. **Preconditions** — structural and semantic preconditions.
7. **Authority requirement** — exact current authority lineage, if any.
8. **Temporal rule** — which clock observation is authoritative and exact boundary
   inclusivity/exclusivity.
9. **Canonicalization/digest rule** — what exact representation is bound when relevant.
10. **Transition** — deterministic accepted state change.
11. **Event production** — exact event type or explicit statement that the operation is
    non-authoritative/non-persisting.
12. **Idempotency** — retry behavior and persisted-stream identity behavior.
13. **Rejection result** — throw/error code, structured rejection, or non-authoritative
    return shape.
14. **Replay obligation** — how equivalent accepted/fabricated history is treated.
15. **Positive conformance** — valid trace that must succeed.
16. **Negative conformance** — minimally mutated invalid trace that must fail.
17. **Compatibility note** — whether the rule is a direct transcription of accepted P0a
    semantics or needs a governance decision.

## 9. Cross-cutting normative domains

### 9.1 Authority/currentness

Rules SHALL distinguish:

- verified root authorization;
- goal binding;
- root grant currentness;
- child-grant attenuation/currentness;
- reservation currentness;
- active plan revision;
- current claim lease;
- fencing generation;
- permit validity/currentness.

A rule SHALL identify which of those are required at that specific boundary. The phrase
"authority must be current" is insufficient without an exact lineage/read-set.

### 9.2 Temporal semantics

S1.1 SHALL define a common temporal convention and then list any operation-specific
exceptions.

The accepted P0a behavior indicates half-open authority windows:

`notBefore <= now < expiresAt`

S1.1 SHALL explicitly define boundary behavior for:

- owner authorization;
- execution grants;
- claim leases;
- permit windows;
- dispatch intent creation time;
- startup `startedAt`;
- worker `reportedAt`;
- authoritative event time monotonicity.

The specification SHALL state when a transition captures `now` and whether every timestamp
in that synchronous authoritative transition is derived from that single observation.

### 9.3 Idempotency versus persisted uniqueness

S1.1 SHALL distinguish two concepts that MUST NOT be conflated:

1. **API retry idempotency:** a retry of the same semantic event/idempotency identity may
   return the already committed event without appending a second event;
2. **persisted stream uniqueness:** a journal prefix containing a second persisted event
   with the same identity/idempotency semantics is invalid under hardened replay.

The specification SHALL define semantic fingerprint equality and the behavior for:

- same `eventId`, same content;
- same `eventId`, different content;
- same `idempotencyKey`, same content;
- same `idempotencyKey`, different content;
- stream-global result/attempt identities.

### 9.4 Structural versus semantic validation

S1.1 SHALL explicitly preserve the accepted split:

- JSON Schema and runtime structural validation define the closed structural data model;
- semantic/cross-record/currentness rules are enforced by the trusted conductor/reducer/
  replay/resource path.

A semantic rule SHALL NOT be added to only one structural validator and then described as
schema/runtime parity.

### 9.5 Canonicalization and digest binding

S1.1 SHALL normatively state the accepted scope of `forge-canonical-json/v0.1`, including:

- finite JSON-compatible values only;
- exact handling of `-0`;
- strict object prototype/data-property requirements;
- own `__proto__` as ordinary data;
- dense arrays only;
- `Array.prototype` exactly;
- no extra/symbol array properties;
- no accessors;
- no inherited/overridden method dispatch during array normalization;
- deterministic key ordering;
- SHA-256 digest format.

S1.1 SHALL also state that this profile is not cross-language JCS conformance.

### 9.6 Resource normalization and replay

S1.1 SHALL distinguish:

- live reservation request input, where duplicate resource entries may be aggregated into a
  canonical request;
- persisted canonical reservation form, where repeated resource entries are not admitted;
- resource definitions as trusted replay input;
- canonical conductor-owned resource state;
- restart hydration and conflicting external seed behavior.

### 9.7 Worker evidence versus authoritative state

S1.1 SHALL normatively preserve:

`worker/startup report != authority != authoritative commit`.

Startup and outcome evidence may be validly shaped yet inadmissible because authority,
plan, lease, permit, or fencing currentness has changed. Late positive evidence SHALL NOT
regain authority by virtue of claiming success.

### 9.8 Uncertainty

S1.1 SHALL define uncertainty as non-terminal evidence and SHALL preserve the accepted
rule that uncertainty alone does not prevent a later legitimate retry.

P0a terminal outcomes remain closed to `succeeded | failed` unless a future superseding
protocol decision changes that domain.

## 10. Error and rejection model

S1.1 SHALL specify not only that invalid transitions fail, but **how** the accepted protocol
represents failure.

The accepted public error domain currently includes:

- `AF_CANONICALIZATION_FAILED`;
- `AF_CONFLICT`;
- `AF_DUPLICATE_ID`;
- `AF_GRANT_REJECTED`;
- `AF_INVALID_EVENT`;
- `AF_INVALID_PLAN`;
- `AF_INVALID_STATE`;
- `AF_NOT_FOUND`;
- `AF_PERMIT_REJECTED`;
- `AF_RESOURCE_EXHAUSTED`;
- `AF_STALE_ATTEMPT`.

S1.1 SHALL classify each normative rejection as one of:

1. thrown `AgentFabricError` with an exact normative code;
2. structured `AuthorityResolution` rejection with normative `reasonCodes`;
3. non-authoritative `unknown`/uncertainty orchestration outcome;
4. idempotent replay of an existing successful semantic event.

S1.1 MUST NOT silently convert a currently accepted structured rejection into a throw (or
vice versa) merely to make the specification aesthetically uniform. Such a change is a
protocol-semantic change and requires explicit governance classification.

The specification MAY declare human-readable error messages non-normative unless a stable
message is needed for machine compatibility. Error **codes/reason categories** used for
programmatic semantics SHALL be explicit.

## 11. Live/replay equivalence contract

S1.1 SHALL define a differential conformance principle:

- any authoritative trace accepted and persisted through the conforming live control path
  MUST be accepted by conforming replay under the same trust inputs;
- any fabricated persisted trace that violates a normative accepted-state invariant MUST
  be rejected by replay even if individual event shapes are structurally valid;
- replay MUST NOT call nondeterministic cognition to reconstruct an accepted control
  decision;
- a public authoritative live transition MUST NOT report success while leaving a journal
  prefix that the same normative replay rules reject.

The specification SHALL distinguish trust-input differences from replay semantic
differences. In particular, journal-origin trust and resource-definition trust are
explicit assumptions, not events inferred from worker data.

## 12. Treatment of `FROZEN_DIRECTION`

S1.1 SHALL preserve `FROZEN_DIRECTION` items as normative architecture constraints, but it
SHALL NOT mark P0a nonconformant for behavior that S1.0 explicitly says is not yet
implemented.

Examples include:

- the broader top-level Agent Fabric decomposition;
- small Trusted Privilege Domain direction;
- evidence/epistemic distinctions not fully implemented in P0a;
- `D-READ-001` read-only semantics for P0b/later.

The S1.1 matrix SHALL use `DIRECTION_ONLY` or an equivalent non-applicable implementation
status for such obligations.

## 13. Treatment of `DEFERRED`

`DEFERRED` capabilities are outside the executable S1.1 P0a conformance target.

S1.1 SHALL NOT create placeholder normative behavior that could later be mistaken for
accepted implementation semantics. If a deferred domain needs an interface reservation,
the text SHALL explicitly label it non-implemented and non-accepted.

## 14. Governance on discovered ambiguity

During S1.1 drafting, every ambiguity SHALL be classified before resolution.

### `CLARIFICATION_ONLY`

Allowed when the accepted implementation/evidence already has one unambiguous behavior and
the new prose simply expresses it precisely.

### `COMPATIBLE_IMPLEMENTATION_REFINEMENT`

Allowed only when behavior is preserved and evidence shows the frozen invariants are
unchanged.

### `EXTENSION_REQUIRED`

Required when S1.1 needs a new semantic case not present in P0a but still compatible with
existing accepted semantics.

### `SUPERSESSION_REQUIRED`

Required when the proposed rule would weaken, change, or contradict a frozen invariant or
trust assumption.

S1.1 SHALL NOT merge with an unresolved `EXTENSION_REQUIRED` or `SUPERSESSION_REQUIRED`
entry hidden inside normative prose. The relevant governance record must be explicit.

## 15. S1.1 acceptance gate

The full S1.1 Normative Kernel SHALL NOT be adopted unless all conditions below hold on one
exact final SHA.

### G-01 — Baseline identity

The S1.1 branch/PR SHALL declare the exact `main` baseline it consumed. Any rebase or
baseline movement that changes relevant Agent Fabric semantics requires the conformance
matrix to be reevaluated.

### G-02 — Complete invariant traceability

Every adopted `I-AUTH-*`, `I-PLAN-*`, `I-EXEC-*`, `I-RES-*`, `I-REPLAY-*`, and
`I-CANON-*` invariant SHALL have an individual matrix row.

No row may be `UNCLASSIFIED`.

### G-03 — Complete operation coverage

Every operation in the S1.1 operation inventory SHALL have a normative rule or an explicit
classification explaining why it is only a helper/composition/non-authoritative operation.

### G-04 — Exact rejection semantics

Every normative rejection path SHALL state its protocol result category and programmatic
error/reason code where the baseline defines one.

### G-05 — Exact idempotency semantics

API retry idempotency and persisted-stream uniqueness SHALL be specified separately.

### G-06 — Exact temporal semantics

Every time-sensitive operation SHALL specify exact inclusive/exclusive boundaries and the
clock observation used by the transition.

### G-07 — Structural/semantic validation boundary

Schema/runtime structural obligations and semantic cross-record obligations SHALL be
separated and internally consistent.

### G-08 — Live/replay differential coverage

The conformance matrix SHALL identify positive live traces and negative fabricated/replay
traces sufficient to demonstrate the normative live/replay contract for every applicable
invariant family.

### G-09 — Coverage gaps resolved or explicitly classified

A testable normative requirement SHALL have positive and negative evidence, or an explicit
tracked gap that blocks S1.1 adoption.

Non-testable trust assumptions and architecture-direction constraints may use explicit
`ASSUMPTION`/`DIRECTION_ONLY` evidence classes rather than synthetic tests.

### G-10 — No silent P0a semantic drift

Any difference between proposed normative semantics and the accepted P0a baseline SHALL be
resolved through the divergence register and, where material, through explicit governance
before S1.1 adoption.

### G-11 — Deferred scope remains deferred

The S1.1 PR SHALL contain no accidental authorization of P0b, production persistence,
consequential effects, recovery, memory, routing, plugins/evolution, production readiness,
or cross-language canonicalization.

### G-12 — Repository gates

The exact final S1.1 SHA SHALL pass all repository checks applicable to its changed paths,
including CI and Security Assurance. Path-filtered checks that do not trigger SHALL be
recorded as `not_applicable`, not falsely reported as passed.

### G-13 — Independent exact-SHA review

A fresh independent read-only review SHALL evaluate the exact final S1.1 SHA and return no
unresolved BLOCKER/HIGH/MEDIUM finding against the S1.1 scope/gate.

### G-14 — Adoption event

S1.1 becomes repository-native normative architecture only when its dedicated PR is merged
to `main`. Drafting, review approval, or green CI alone do not constitute adoption.

## 16. Review focus for the S1.1 PR

Independent review SHALL explicitly test for:

- prose that accidentally grants authority to strategy/model output;
- conflation of offer/claim/permit/execution/outcome;
- weakening of transitive revocation/expiry/reservation currentness;
- missing temporal boundary definitions;
- idempotency/replay contradictions;
- schema/runtime/replay inconsistency;
- error-code drift relative to accepted behavior;
- canonicalization wording broader than the accepted strict JSON model;
- claims that P0a proves production persistence/security;
- hidden P0b or consequential-effect semantics;
- invariant rows whose evidence does not actually exercise the stated requirement.

## 17. Exit condition of this planning record

This scope/gate planning record may be adopted before the full normative kernel. Its
adoption means only:

- the repository has agreed what S1.1 must specify;
- the required deliverables and acceptance gate are fixed enough to begin drafting;
- the current coverage gaps are visible;
- S1.1 itself is **not yet adopted**;
- P0b is **not authorized**.

The next implementation step after adopting this planning record is to draft
`S1.1_NORMATIVE_KERNEL.md` and the final conformance matrix against the baseline declared
here.
