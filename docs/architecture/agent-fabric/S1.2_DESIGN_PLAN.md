## 2. Component inspection inventory

Source paths are under `src/forge/agent-fabric/` unless otherwise stated.

| Component | Initial inspection target | Question the complete design must resolve |

| Authority | `authority.ts` | Which helpers check shape/scope/currentness/lineage, and which return structured rejection versus throw? |
| Resource accounting | `resource-ledger.ts` plus conductor/reducer projections | Who owns mutable state, reservation transaction, normalization, seed hydration and rollback? |
| Planning | `planning.ts` | Which helpers construct/derive content and which trusted transition activates it? |
| Canonical and structural input | `canonical.ts`, `validation.ts`, `errors.ts`; `schemas/agent-fabric/v0.1/control-event.schema.json` | Where do JSON shape, canonical representation and semantic acceptance differ? |

Do not infer a service/process/deployment boundary merely from a filename or class. For
example, exported MemoryControlJournal and authority helpers do not independently provide
all guarantees of the hardened control path. A reference implementation diagram must
state that applicability rather than promote a helper to an alternate authority ingress.

## 4. Required sequence and ownership cases

| Case | Source/evidence to start with | Required design distinction |
| --- | --- | --- |
| Verified ingress → goal → root grant | authority, conductor, journal/replay; S11-TRACE/SEMANTIC | trusted verifier and exact GoalContract lineage versus content hash alone |
| Derive/reserve → failed append | ledger transaction and replay-validating append; existing P0a rollback vector | earlier initialization event versus atomic reservation/grant pair; memory rollback versus production transactions |
| Intent → offer → claim → permit | conductor; S11-OFFER/CLAIM/BINDING | scheduling claim before grant selection; no authority from offer; 11 bound permit fields |
| Lease expiry → new fenced attempt | conductor/replay; S11-LEASE/FENCE/EXPIRY/TIME | half-open time/currentness, current generation, no assumption of physical worker termination |
| Startup/result evidence → admission or uncertainty | p0a/conductor; S11-UNCERTAINTY and historical late-positive regressions | authoritative commit versus observation, initial guard failure versus adapter recovery path |
| API retry versus duplicate stream | journal/conductor/replay; S11-IDEMPOTENCY/REJECTIONS | method guards before append retry; exact prior outcome; no duplicate persisted identity |
| Resume + resource lifecycle | hardened constructor/ledger/reducer; S11-RESTART | internal ownership, trusted definitions, unchanged spent consumption/counters, release of capacity |
| Malformed/canonical/semantic input | validators/canonical/replay; S11-CANON/ERROR/SCHEMA | real schema shape versus semantic uniqueness and canonical JS admission; error preservation |

For each case, show caller inputs, trusted inputs, source symbols, state read/owned/write
sets, sequence of checks, success result, earliest rejection and any already committed
state on failure. Link existing vectors by exact test name or stable S11 prefix.
Do not invent a new invariant to make the diagram uniform.

## 5. Traceability and decision record shapes

Each OP row in the complete traceability artifact must resolve:

```text
operation_id; normative_reference; invariant_ids[]; applicability
source_baseline; public_entrypoint; internal_symbols[]
trusted_inputs[]; untrusted_inputs[]; state_owner; read_set[]; write_set[]
guard_order; clock_observation; clone_or_snapshot_boundary
event_type_or_none; journal_boundary; replay_symbols[]
success_result; rejection_or_reason_codes; retry_behavior; failure_atomicity
existing_positive_vectors[]; existing_negative_vectors[]
evidence_class (OBSERVED / INFERRED / PROPOSED); mapping_status; decision_refs[]
```

Each I row must resolve `invariant_id`, adopted applicability/coverage, OP links, enforcing
or structural component references, positive/negative evidence (or explicit assumption/
direction applicability), and unresolved mapping/decision references. Map journal origin,
verifier trust and trusted definitions as applicability inputs, not synthetic proofs of
real-world authenticity.

Use `MAPPED` only for a completed, source-supported mapping. Use `OPEN_MAPPING` during
drafting; an unresolved applicable mapping becomes `BLOCKING_GAP` at adoption review.
Use `NOT_APPLICABLE` only for a particular field with a reason, such as no event for an
offer or no control-state write for a pure canonical helper. It must not hide an entire
adopted operation or invariant.

Each decision record must include:

```text
decision_id; affected_OP_and_I_ids[]; exact_baseline_fact; proposed_interpretation
source_and_vector_evidence[]; divergence_class; compatibility_impact
in_scope_dependency (yes/no); resolution_or_deferred_reason; required_separate_decision
```

The five S1.1 clarification records are mandatory cross-checks. No copied decision should
be called newly adopted solely because it was moved into the S1.2 document. Optional
refinements remain proposals, and a required unresolved extension/supersession blocks
adoption as specified by the scope gate.

## 6. Verification plan and downstream handoff

For this planning PR, verify adoption SHAs/parents/run IDs, local document links, counts
of planned OP/I coverage, consistency of scope versus gate, and a documentary-only diff.
For the full design, additionally check each actual source/symbol/vector reference and
the correctness of the sequences and ownership tables. Follow applicable repository
verification instructions, recording exact commands, outcomes and limitations.

CI for a future SHA is new evidence. Historical S1.1 green runs cannot satisfy S1.2's
repository gate. Path-filtered jobs that do not trigger are `not_applicable`. An unrelated
local failure must be investigated and disclosed with its provenance; it does not permit
silent test exclusions, false green status or broad repairs inside this documentary slice.

Existing protocol tests are the starting evidence; this plan does not require a new
generic runner, copied tests or production execution. The later S1.3 Proof & Conformance
scope may consume the adopted kernel, obligation catalog and completed design mappings,
but is not opened or implemented by adopting this plan. Any later runtime slice likewise
requires its own scoped authorization. P0b remains outside the authorized work.
