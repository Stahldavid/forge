**Gate:** [S1.3_SCOPE_AND_GATE.md](./S1.3_SCOPE_AND_GATE.md)

## 1. Purpose of this plan

This plan turns the proposed S1.3 scope into a reviewable work sequence for the first
limited stage, S1.3-A — Evidence Registry & Reproduction Baseline. It consumes the adopted
S1.1 rule IDs and S1.2 implementation mappings; it does not create a second protocol
specification.

The plan is evidence-first. Before choosing a generic runner, model checker, signature
scheme, cross-language harness or retention service, it requires a complete inventory of
what the repository already knows, how that knowledge was observed and which concrete gaps
remain.

## 4. Stable evidence identifiers

S1.3-A must allocate immutable evidence IDs. Recommended format:

```text
AF-EV-0001
AF-EV-0002
...
```

A human-readable alias such as `S11-FENCE`, `E-F01` or `CI-283` may be retained, but aliases
are not globally unique evidence identities. Once an evidence ID is adopted, later reruns
create new evidence records linked through `reproduces`/`supersedes_observation` metadata;
they do not mutate the historical observation in place.

A single test parameterization may yield multiple evidence records when materially
different dimensions support different claims. Conversely, one execution may support
multiple OP/I IDs if the supported claim and limitations are explicitly stated.

## 5. Evidence binding rules

### 5.1 Source state versus execution state

Every record distinguishes:

- `subject_sha`: the source state the claim is about;
- `execution_sha_or_state`: the exact commit or captured worktree state actually executed;
- optional `adoption_merge_sha`: the merge that later adopted reviewed evidence.

For a clean checkout where `subject_sha == execution_sha`, the evidence may be called
exact-SHA executed evidence. A local run from a dirty worktree must capture the diff/state
or be marked unable to prove the bare SHA. A statement such as “same code as baseline” is
not a substitute for these coordinates.

### 5.2 GitHub workflow evidence

A workflow record must capture:

```text
repository
workflow name
run ID
job/matrix identity where relevant
head SHA
event/trigger
result status
relevant step/test summary
artifact/log reference where retained
```

A workflow that did not trigger because of path filters is `NOT_APPLICABLE`, not `PASS`.
A matrix workflow may need separate evidence records when OS/runtime differences are part
of the claim.

### 5.3 Local evidence

A local record must capture, as applicable:

```text
exact commit/worktree state
command and cwd
OS/architecture
Bun/Node/package-manager/tool versions
dependency/lock state
relevant environment or fixture prerequisites
timeout/deadline
exit status
observed counts/output summary
retained log or report location
```

Secrets, credentials and sensitive values must not be copied into evidence records. Record
only the non-secret configuration facts necessary to reproduce the observation.

### 5.4 Static/source evidence

`SOURCE_MAPPING`, `STRUCTURAL_EVIDENCE`, `ASSUMPTION` and `DIRECTION_ONLY` records bind to
an exact source/document SHA and source location. They do not receive a fabricated executed
`PASS`. If a source claim is later executable, the execution becomes a separate record.

## 6. Reproduction protocol

Every evidence item marked reproducible must provide or inherit a procedure containing:

1. exact repository/source state;
2. prerequisites and environment;
3. command/workflow and working directory;
4. expected observation and result status;
5. timeout/deadline where relevant;
6. output/log location;
7. cleanup or fixture-reset requirement;
8. known nondeterminism or environmental dependencies.

### Retry discipline

- A failed/timed-out attempt remains an evidence record.
- A retry creates another record; it does not replace the first result.
- A final classification may become `INCONCLUSIVE` when attempts disagree and no cause is
  established.
- “Passed in isolation” and “failed in broad run” are distinct observations and both remain
  visible.
- Increasing a timeout to obtain green is a behavior/tooling change and requires explicit
  scope if the adopted procedure changes materially.

### Historical reproduction

If a historical bug/repair is reproduced on an old SHA, that execution is bound to the old
SHA and does not imply the current baseline still contains the defect. A repaired current
baseline should link the historical negative and current positive evidence rather than
rewriting either.

## 8. Gap register record shape

Every gap must have:

```text
gap_id
class
affected_OP_I_event_ids[]
exact_observed_problem
existing_evidence_ids[]
blocking_impact
minimum_closure_evidence
candidate_action
requires_code_or_test_change (yes/no)

```

No gap may be closed merely because a later broad suite is green. Closure evidence must
address the actual missing/failed claim.

A code/protocol defect discovered during S1.3 is reported separately with severity and the
existing governance classification. The evidence catalog may describe the defect but cannot
silently fix or supersede it.

## 9. First-pass gap review checklist

For each OP/I/event, S1.3-A must ask at least:

- Is there an exact positive vector?
- Is there an applicable negative/adversarial vector?
- For authoritative transitions, is replay/candidate-replay evidence present?
- For time-sensitive rules, are equality and expiry boundaries represented?
- For identity/idempotency rules, are prior-result and invalid persisted-duplicate cases
  distinct?
- For resource operations, are all three resource semantics represented where applicable?
- For authority, does evidence separate content identity from current authority?
- For structural/schema claims, is actual schema/runtime parity evidence distinct from
  semantic replay evidence?
- Does the evidence refer to the correct historical/current SHA?
- Can the result be reproduced with a documented procedure?
- Are local/environmental failures preserved rather than omitted?
- Is any claimed authenticity/durability actually only an assumption?

This checklist is diagnostic; it is not a requirement to add a new test for every cell.
A missing direct vector becomes a classified gap whose importance must be reviewed.

## 10. Tooling-need evaluation records

A `TOOLING_CANDIDATE` gap must produce a decision proposal before implementation. The
proposal must state:

```text
tooling_decision_id
observed_gap_ids[]
why existing tests/workflows/docs are insufficient
minimum capability required
semantic authority boundary
new dependencies/runtime/workflow effects
failure and trust model
how output binds to exact source SHA
how false green / stale evidence is prevented
migration/compatibility impact
separate implementation and acceptance gate
```

### Generic runner

A runner is justified only after the evidence record schema and reproduction contract are
stable enough to automate without embedding a second interpretation of the protocol. It
must consume adopted OP/I IDs; it must not invent replacement semantics from source code.

### Model checking

A model-checking proposal must identify the exact invariant/property, state abstraction,
transition correspondence to S1.1 and known abstraction loss. Counterexamples must be
validated against the implementation or normative model before being treated as defects.
A green model cannot prove properties omitted by the abstraction.

### Signing/provenance

A signing proposal requires an explicit threat model, key lifecycle, signer/verifier roles,
what bytes are signed and what trust assertion the signature adds. Signing test output does
not make the test semantically correct.

### Cross-language conformance

A cross-language proposal requires either a second implementation or a separately adopted
cross-language representation/canonicalization objective. The current
`forge-canonical-json/v0.1` JS/TS profile is explicitly not JCS.

### Evidence retention

A retention proposal requires an explicit durability/audit requirement, retention horizon,
artifact identity and deletion/access model. Existing GitHub/repository retention is the
current evidence source and is not silently declared production-grade.

## 13. Downstream boundary

After S13-P08, a dedicated S1.3-A PR may produce only the evidence/reproduction baseline
defined by the adopted planning package. It must not bundle runtime/test/tooling changes.
If that work reveals a required test vector, defect repair or tooling need, open a separate
scope and acceptance path tied to the exact gap.

Only after S1.3-A is adopted should the project decide whether a further Proof & Conformance
stage is necessary and what it contains. A generic runner, formal model, signature scheme,
cross-language harness or retention service is **not** the default next step.

S1.3 planning and S1.3-A do not authorize P0b. P0b requires its own objective, scope,
implementation evidence, independent review and adoption decision.
