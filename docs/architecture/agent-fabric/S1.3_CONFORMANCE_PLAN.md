**Baseline:** `main@d2f426b1577d457bc6609c4d8e88ef7a055a1a23`

**Gate:** [S1.3_SCOPE_AND_GATE.md](./S1.3_SCOPE_AND_GATE.md)

## 1. Purpose

This plan turns the proposed S1.3 scope into a reviewable work sequence for the first
limited stage, **S1.3-A — Evidence Registry & Reproduction Baseline**. It consumes the
adopted S1.1 rule IDs and S1.2 implementation mappings; it does not create a second
protocol specification.

The plan is evidence-first. Before selecting a generic runner, model checker, signature
scheme, cross-language harness, machine-readable catalog or retention service, it requires
a complete inventory of what the repository already knows, how that knowledge was observed
and which concrete gaps remain.

## 4. Evidence identity and binding

Use immutable evidence IDs such as `AF-EV-0001`. Existing aliases (`S11-FENCE`, `E-F01`,
`CI-283`) may be retained as aliases but are not the canonical evidence identity.

Every record distinguishes:

- `subject_sha`: source state the claim concerns;
- `execution_sha_or_state`: exact commit or captured worktree state actually observed;
- optional `adoption_merge_sha`: historical merge that later adopted reviewed evidence.

A clean checkout where subject and execution SHA match can be called exact-SHA evidence.
A dirty local worktree must capture its diff/state; otherwise the observation cannot be
claimed as evidence for the bare commit.

### Minimum evidence record

```text
evidence_id

source_or_test_ref
subject_sha
execution_sha_or_state

```

Static source/structural/assumption/direction records use `NOT_APPLICABLE` for execution
fields rather than fabricating a test result.

## 5. Workflow and local provenance

### GitHub workflow evidence

Capture repository, workflow, run ID, job/matrix identity where relevant, head SHA,
trigger, result, relevant step/test summary and artifact/log reference. Path-filtered jobs
that do not trigger are `NOT_APPLICABLE`, not `PASS`.

### Local evidence

Capture exact commit/worktree state, command/cwd, OS/architecture, Bun/Node/tool versions,
dependency/lock state, non-secret fixture prerequisites, timeout/deadline, exit status,
observed summary and retained report/log location.

Never copy credentials or secret values into evidence records.

## 6. Reproduction protocol

Every evidence item marked reproducible must provide or inherit:

1. exact source state;
2. prerequisites/environment;
3. command/workflow and working directory;
4. expected observation and status;
5. timeout/deadline where relevant;
6. output/log location;
7. fixture/reset/cleanup requirement;
8. known nondeterminism/environmental dependencies.

### Retry discipline

- failed/timed-out attempts remain evidence records;
- retries create new records instead of replacing earlier observations;
- disagreement without root cause may yield `INCONCLUSIVE`;
- broad-run failure and isolated pass are separate observations;
- changing timeout/test/workflow behavior to obtain green requires separate scope when it
  materially changes the adopted procedure.

Historical bug reproductions remain bound to the historical SHA. A current repaired result
links to the historical negative; it does not rewrite it.

## 8. Gap register

Every gap resolves:

```text
gap_id
class
affected_OP_I_event_ids[]
exact_observed_problem
existing_evidence_ids[]
blocking_impact
minimum_closure_evidence
candidate_action
requires_code_or_test_change (yes/no)
requires_new_tooling (yes/no/undetermined)
tooling_decision_ref
status
```

No gap is closed merely because a later broad suite is green. Closure evidence must address
the actual claim. A protocol/code defect discovered during S1.3 uses the existing severity
and governance process; the evidence catalog cannot silently repair or supersede it.

A `BLOCKING_GAP` blocks the affected conformance claim or later promotion. It does **not**
block adoption of an accurate S1.3-A evidence baseline whose purpose is to record that gap.
The matrix must not label an affected claim `SUPPORTED` while its blocking gap remains open.

## 9. First-pass review checklist

For every OP/I/event ask:

- Is there an exact positive vector?
- Is there an applicable negative/adversarial vector?
- For authoritative transitions, is candidate/offline replay evidence present?
- For time rules, are equality and expiry boundaries represented?
- For idempotency, are prior-result and invalid persisted-duplicate cases distinct?
- For resources, are all three semantics represented where applicable?
- For authority, is content identity separated from current authority?
- Is schema/runtime parity distinct from semantic replay?
- Does each claim point to the correct historical/current SHA?
- Can the observation be reproduced from recorded procedure/environment?
- Are failing/time-out/NA observations preserved?
- Are authenticity/durability claims actually assumptions rather than repository proof?

This checklist diagnoses evidence quality; it does not require a new test for every cell.
Missing direct evidence becomes a classified gap whose importance is reviewed.

## 10. Tooling-need decisions

A `TOOLING_CANDIDATE` gap must produce a decision proposal before implementation:

```text
tooling_decision_id
observed_gap_ids[]
why existing tests/workflows/docs are insufficient
minimum capability required
semantic authority boundary
new dependencies/runtime/workflow effects
failure and trust model
exact-SHA output binding
false-green/stale-evidence controls
compatibility impact
separate implementation and acceptance gate
```

A generic runner is justified only after the evidence/reproduction schema is stable and
manual execution/binding is demonstrably inadequate. A model checker requires a named
property, traceable abstraction and explicit abstraction loss. Signing requires a threat
model and key lifecycle. Cross-language conformance requires a second implementation or a
separately adopted cross-language profile. Retention infrastructure requires an explicit
durability/audit need. None is a default consequence of S1.3.

## 11. Planned S1.3-A sequence

| Step | Work | Completion condition |
| --- | --- | --- |
| 1 | Freeze adopted S1.3 planning and exact evidence-subject baseline. | coordinates and relevant baseline movement recorded |
| 2 | Allocate evidence IDs and ingest historical acceptance metadata. | P0a/S1.1/S1.2/F01/F02 represented without rewriting history |
| 3 | Resolve source/test/workflow references. | every evidence record has an exact repository/source/run reference |
| 4 | Build 24 OP / 35 I / 16 event cross-index. | no orphan accepted rule/event; applicability preserved |
| 5 | Write reproduction procedures. | procedure explicit or `REPRODUCTION_GAP` recorded |
| 6 | Reproduce a representative/current set using existing commands only. | observations recorded individually, including failures/timeouts/NA |
| 7 | Perform gap review. | every unresolved item classified with blocking impact/minimum closure evidence |
| 8 | Evaluate tooling need from actual gaps. | each proposed tool has a need record or is unnecessary/deferred |
| 9 | Check links/counts/statuses/diff and repository gates. | exact-final-SHA evidence; no false pass/hidden local failures |
| 10 | Independent review and explicit adoption. | zero unresolved review BLOCKER/HIGH/MEDIUM; all evidence gaps explicitly classified; authorized merge |

The independent review gate assesses whether the evidence baseline is truthful and
complete **as an inventory**. It does not require all conformance gaps to be closed before
the inventory can be adopted.

## 13. Downstream boundary

After S13-P08, a dedicated S1.3-A PR may produce only the evidence/reproduction baseline
defined by the adopted planning package. It must not bundle runtime/test/tooling changes.
If it records a required vector, defect repair or tooling need, open a separate scope tied
to the exact gap.

S1.3-A may be adopted with explicitly classified `BLOCKING_GAP` entries; those entries
prevent stronger conformance claims or promotion for affected rules until separately
closed. Only after the evidence baseline is adopted should the project decide whether a
further Proof & Conformance stage is necessary and what it contains.

A generic runner, formal model, signature scheme, cross-language harness or retention
service is **not** the default next step. S1.3 planning and S1.3-A do not authorize P0b.
