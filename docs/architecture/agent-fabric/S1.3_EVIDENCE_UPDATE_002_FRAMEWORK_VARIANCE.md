## 1. Purpose

The adopted S1.3-A gap register retains:

- `S13-GAP-002 — local framework verification variance`, class `ENVIRONMENT_VARIANCE_GAP`;
- `S13-GAP-008 — historical local-framework record lacks exact S1.3 minimum metadata`, class `EVIDENCE_METADATA_GAP`.

This evidence update performs a controlled repository-hosted reproduction designed to separate four possible causes that had previously been conflated in broad local observations:

This update is evidence/classification only. It does not change runtime behavior, tests, timeouts, generated artifacts, workflows used by production/repository gates, dependencies or Agent Fabric semantics.

### 3.1 Generated drift is deterministic within OS family, but OS-dependent

On the same exact subject:

- Linux Node 22 and Node 24: `generated drift: 121 artifact(s) would change`;
- Windows Node 22 and Node 24: `generated drift: 154 artifact(s) would change`.

Therefore the pristine repository state is not `forge generate --check` clean in either OS family, and the observed generated output set is itself environment-sensitive. This rules out a blanket recommendation to simply commit one environment's generated result without first defining/validating canonical generation semantics.

On Linux, strict TestGraph itself completed with zero failed chunks in both Node versions. The broad `verify framework` exit `1` was driven by the drift-related internal checks:

```text
fail generate-check
fail agent-contract-check
fail rls-check
```

This is consistent with the previously retained Security workflow diagnostics.

### 3.2 Windows adds independent strict-TestGraph failures

On both Windows/Node 22 and Windows/Node 24, strict TestGraph additionally failed for two reproducible environment/portability reasons:

1. `tests/cli/field-test.test.ts` expected the string `scripts/field-test-forgeos.mjs`, while the Windows command contained the native path `D:\\a\\forge\\forge\\scripts\\field-test-forgeos.mjs`. The test uses a slash-sensitive substring assertion and therefore fails on the Windows separator even though the packaged harness path is otherwise the expected file.
2. `tests/external-manifest/java-adapter-conformance.test.ts` failed with `ENOENT ... uv_spawn 'mvn'` because Maven was not available on the Windows hosted runner used by the diagnostic.

These are distinct from generated drift and distinct from the historical H48/external-HTTP timeout observations.

### 3.3 Focused historical timeout suspects did not reproduce

Across all four cells:

- `tests/agent-memory/h48-agent-memory.test.ts` exited `0`;
- `tests/external-manifest/external-runtime-node-cli.test.ts` exited `0`.

The H48 open-stdin probe itself passed within its expected bounded behavior in the retained logs. The focused external runtime file also passed.

Therefore the controlled repository-hosted reproduction does **not** support classifying either focused test as a deterministic defect on `de944964…` under these four environments.

It also does not erase the prior local failures: those remain historical observations in a different environment/state.

## 5. Security workflow masking remains a separate repository-gate issue

The adopted Security workflow runs several diagnostic commands through pipelines of the form:

```text
command | tee evidence-file
```

without pipeline-failure propagation. Historical/final S1.3-A Security evidence therefore correctly retained cases where the workflow/step conclusion was `SUCCESS` while the command output itself contained failing internal checks.

The controlled reproduction confirms those internal failures are not imaginary: on pristine Linux exact subject the same broad framework surface exits `1` because generated drift is present.

This evidence update does not change the Security workflow. A future workflow-hardening proposal must not simply add `pipefail` while the current pristine generated-state contract is unresolved, because doing so would intentionally turn the existing Security gate red on the currently adopted repository state. Generated-state policy and false-green handling should be scoped explicitly rather than repaired accidentally in an evidence PR.

## 6. Classification of S13-GAP-002

The controlled matrix materially narrows `S13-GAP-002`.

The previous broad phrase “local framework verification variance” decomposes into at least these independently evidenced mechanisms:

1. **Pristine generated drift:** deterministic in both tested Node versions, with OS-dependent artifact count (Linux 121, Windows 154).
2. **Linux state dependence:** pristine broad verify fails; post-`generate` broad verify passes.
3. **Windows portability/prerequisite failures:** slash-sensitive field-test assertion and Maven absence persist after generation.
4. **Windows generated agent-export state:** generic/Codex agent-adapter stale-export diagnostics persist after generation.
5. **Historical H48/external-HTTP local timeouts:** not reproduced in any focused cell here; both focused files pass before and after generation on Linux/Windows, Node 22/24.

Proposed disposition:

```text
S13-GAP-002
class: ENVIRONMENT_VARIANCE_GAP
status: OPEN, materially narrowed/classified
blocking impact: unchanged — blocks claims that broad local verify is deterministic/green across environments; does not establish an Agent Fabric semantic failure
```

The gap should remain open because the original local machine/state that produced the retained H48 and external-HTTP failures has not been reproduced with the exact same environment metadata, and Windows broad verification still has independently reproducible portability/prerequisite failures.

No timeout increase is justified by this evidence.

## 8. Repair decisions supported by this evidence

### 8.1 Not justified

This evidence does **not** justify:

- blanket test-timeout increases;
- H48 timeout changes;
- external HTTP runtime timeout changes;
- treating Security workflow `SUCCESS` as aggregate framework success;
- committing one OS's generated artifacts as a blind repair;
- closing GAP-008 by substituting GitHub-hosted evidence for missing historical local metadata.

### 8.2 Narrow future proposals that are now justified for separate review

The evidence is sufficient to justify separate, narrowly scoped proposals for:

1. **Windows field-test portability:** make the assertion path-separator independent without changing field-test runtime semantics.
2. **Java conformance prerequisite policy:** explicitly decide whether Maven is a required prerequisite for broad Windows TestGraph, a conditionally skipped external-tool check, or a provisioned workflow dependency; do not silently treat ENOENT as protocol failure.
3. **Generated-state contract:** determine why exact subject is not `generate --check` clean and why the generated artifact count differs by OS before committing generated output or hardening the Security gate.
4. **Security pipeline false-green hardening:** after the intended generated-state contract is resolved, make piped command failures propagate rather than relying on `tee`'s exit status.
5. **Windows agent-adapter stale exports:** isolate whether `forge generate` must also refresh `.forge/agent/context.json` / `commands.json` or whether broad verify is reading stale operational state that should not participate in a clean repository check.

Each repair should have its own scope and acceptance evidence. They should not be bundled into this evidence update.
