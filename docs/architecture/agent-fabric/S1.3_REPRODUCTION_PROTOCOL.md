# S1.3-A — Reproduction Protocol

**Record ID:** `AF-S1.3-A-REPRODUCTION-2026-09-12`

**Status:** `IMPLEMENTATION_CANDIDATE`; not adopted.

**Adopted planning baseline:** `main@801c2192e64652ade19a642b2f09f8660963c74f`.

**Current repository / reproduction baseline:** `main@92c470ae2319aed9bde734d4506767677abe5a3c`.

The baseline movement assessment is in the evidence catalog section 1.1. Historical
attempts retain their original subjects; fresh S13-A12 execution must use the final
candidate containing the separately adopted PR #20 repair. Neither that repair's passing
runs nor a prior PR #19 run is transferable to the new final SHA.

This protocol defines how S1.3-A observations are bound to source state, workflow association,
actual execution state, environment, result and retained provenance. It does not add a runner,
workflow, dependency, new test, timeout policy or runtime behavior.

## 1. Reproduction principles

1. **Bind the state actually observed.** `subject_sha`, `workflow_head_sha`,
   `checked_out_commit_sha`, `execution_sha_or_state` and `adoption_merge_sha` are distinct
   coordinates. A workflow associated with commit B cannot be called an exact execution of B
   unless the checkout actually established B.
2. **A pull-request workflow head is an association coordinate, not execution proof.** GitHub
   `pull_request` workflows may check out `refs/pull/<n>/merge`; when that happens the
   synthetic merge commit is the execution coordinate. Never copy the workflow head into
   `execution_sha_or_state` merely because the run is associated with that head.
3. **Tree equivalence requires proof.** A synthetic merge or later adoption merge may be
   described as content-equivalent to a reviewed head only when the relevant tree SHAs are
   both established and equal. Tree equality does not rename one commit as another.
4. **Unknown checkout remains unknown.** If the historical checkout cannot be recovered,
   record `CHECKOUT_NOT_ESTABLISHED` plus `EVIDENCE_METADATA_GAP`; never infer the head.
5. **Clean worktree means exact SHA.** A local run is `exact-sha` only when the worktree and
   index match the named commit before execution. If generation or the command modifies the
   tree, capture that fact and restore/record it before subsequent exact-sha claims.
6. **History is immutable evidence.** Historical failures, timeouts, retries and path-filtered
   non-runs are retained. A later pass creates a new evidence record.
7. **Expected observation is explicit before interpretation.** A green workflow conclusion
   does not close a narrow gap, and a successful shell step does not erase failing diagnostics
   printed inside that step.
8. **Evidence is not authority.** Reproduction metadata cannot change S1.1 semantics,
   authorize a grant/effect, or turn a deferred capability into an accepted one.
9. **No secret material.** Record non-secret configuration and prerequisites only; do not
   persist tokens, credentials, personal data or secret values in the evidence catalog.

## 2. Exact-state procedure

### 2.1 Local clean checkout

For a local reproduction intended to support an exact SHA:

```bash
git status --short
git rev-parse HEAD
git diff --exit-code
git diff --cached --exit-code
```

The expected precondition is:

```text
HEAD == execution_sha_or_state
working tree clean
index clean
```

If any condition fails, do **not** label the run exact-sha. Record the dirty state by commit
plus retained diff/patch identifier, or classify the reproduction as blocked/inconclusive if
that state cannot be preserved.

### 2.2 Dependency state

Use the repository lockfile and the package-manager invocation already used by accepted
repository workflows unless the historical record explicitly requires another environment:

```bash
bun install --frozen-lockfile --ignore-scripts
```

Record Bun/Node versions, OS/architecture and whether dependencies were newly installed or
already present. A dependency update is not permitted inside S1.3-A.

## 4. GitHub workflow evidence

### 4.1 Required provenance fields

For every GitHub run used as evidence, record the following coordinates separately:

```text
subject_sha
workflow_head_sha
workflow_base_sha
checkout_ref
checked_out_commit_sha
execution_sha_or_state
workflow_head_tree_sha
execution_tree_sha
tree_equivalence_status
tree_equivalence_evidence_ref
adoption_merge_sha
```

Also retain:

```text
repository
workflow name
run ID and attempt
trigger
job name and matrix identity when claim depends on it
step/test summary relevant to the claim
conclusion
artifact/log reference if retained
```

Rules:

1. `workflow_head_sha` is the commit the workflow is associated with according to GitHub
   metadata. It is not automatically the execution commit.
2. `checked_out_commit_sha` comes from checkout/log evidence (for example the fetched ref,
   `HEAD is now at ...`, or `git log -1 --format=%H`).
3. `execution_sha_or_state = checked_out_commit_sha` when checkout is established.
4. If checkout is not recoverable, both `checked_out_commit_sha` and
   `execution_sha_or_state` are `CHECKOUT_NOT_ESTABLISHED`; attach
   `EVIDENCE_METADATA_GAP`.
5. `tree_equivalence_status` may be `PROVED_EQUAL`, `PROVED_DIFFERENT`, `NOT_CHECKED`, or
   `NOT_APPLICABLE`. `PROVED_EQUAL` requires retained evidence for both tree SHAs.
6. A synthetic PR merge remains a synthetic merge even when its tree equals the reviewed
   head tree. The reviewed head may remain the evidence subject; it must not be relabeled as
   the execution SHA.
7. `adoption_merge_sha` is a later governance/adoption coordinate only. It is never an
   execution coordinate unless a run actually checked out that commit.

### 4.2 Pull-request checkout rule

For `pull_request` workflows, inspect the checkout step before making any exact-head claim.
A typical default checkout may fetch:

```text
refs/pull/<pr>/merge
```

If so, record:

```text
checkout_ref = refs/pull/<pr>/merge
checked_out_commit_sha = <synthetic merge SHA from the log>
execution_sha_or_state = <same synthetic merge SHA>
```

The workflow head remains separately recorded as `workflow_head_sha`.

### 4.3 CI workflow

The repository CI is broad evidence, not a single protocol vector. When used, distinguish:

- `verify` job: typecheck, unit/integration, generation, compiler workspace, example drift,
  package/template smoke and packed package smoke as actually present in the run;
- external quickstart job;
- Node/OS matrix jobs.

A `SUCCESS` run does not imply a specific test vector existed unless the source/test record
shows that vector was in the executed suite at the established execution state. If an early
step mutates the worktree, later steps are not clean-checkout evidence unless the resulting
state is separately bound.

### 4.4 Security Assurance

Record the exact Security Assurance run and the steps that completed. A successful workflow
conclusion is repository-gate evidence only. If a step prints failing subchecks (for example
`generate-check`, `agent-contract-check`, or `rls-check`) while shell/pipeline semantics still
return success, preserve both facts; do not summarize the internal verification as green.

### 4.5 Path-filtered workflows

If a workflow did not trigger because the diff did not match its `pull_request.paths`, the
record is:

```text
result_status = NOT_APPLICABLE
actual_observation = workflow did not trigger under path filter
```

Do not create a synthetic successful run or reuse a run from an older SHA as the current
candidate gate.

## 5. Local environment record

A local executed evidence record should include, where applicable:

```text
OS and version
architecture
Node version
Bun version
package-manager version
lockfile state
cwd
command
relevant non-secret environment flags/fixture prerequisites
timeout/deadline

```

If the existing historical source does not preserve one of these fields, record an
`EVIDENCE_METADATA_GAP`; do not reconstruct it from memory.

## 6. Result normalization

Use exactly these statuses for executed evidence:

| Status | Meaning |
| --- | --- |
| `PASS` | the stated expected observation was obtained for the bound execution state |
| `FAIL` | the stated expected observation was not obtained |
| `SKIPPED` | an existing test/job was intentionally not executed |
| `NOT_APPLICABLE` | the check does not apply to the scoped claim/change, with reason |
| `BLOCKED` | execution could not proceed because a named prerequisite was unavailable |
| `INCONCLUSIVE` | execution occurred but variance, timeout, mixed subresults or insufficient observation prevents a responsible pass/fail claim |

A process exit code of zero or workflow conclusion of success is not automatically `PASS`:
for a diagnostic script, pipeline, or step that retains failing internal diagnostics, the
evidence record must describe the actual observation.

## 7. Retry and timeout discipline

1. A retry creates a **new evidence record** or attempt reference.
2. Do not delete or mutate the earlier failed/timed-out observation.
3. If broad and isolated runs disagree without a root cause, current disposition is
   `INCONCLUSIVE`; link both attempts.
4. Increasing a timeout to obtain green is a procedure/tooling change. S1.3-A may recommend
   it but cannot change repository timeouts.
5. GitHub automatic/manual reruns preserve the original run ID/attempt and the rerun
   attempt identity; do not collapse attempts into a single pass.
6. For flaky/environment-sensitive evidence, record the minimum closure evidence in the gap
   register rather than repeatedly rerunning until green.

## 8. Historical bug / repair reproduction

For S12-F01 or S12-F02:

- historical negative observation remains bound to the pre-repair baseline;
- repair-positive evidence remains bound to its subject/reviewed repair head;
- the workflow association head and actual checkout/execution coordinates remain separate;
- adoption merge is a separate coordinate;
- a current run of the repair regression is a new reproduction record;
- do not claim that a historical bug exists on the current baseline solely because its old
  diagnostic still appears in documentation.

The same rule applies to earlier P0a review findings and later fixes.

## 11. Current S1.3-A PR evidence procedure

For the dedicated S1.3-A PR:

1. keep the diff documentary/evidence-organization only;
2. record the exact final candidate SHA as `subject_sha`/`workflow_head_sha` where applicable;
3. for every final-candidate workflow, extract `checkout_ref` and
   `checked_out_commit_sha` from the actual checkout evidence;
4. use only runs associated with the exact final candidate for S13-A12, while separately
   preserving the real execution coordinate;
5. if S13-A12 requires **exact-SHA execution**, a synthetic merge does not satisfy that
   wording merely because the workflow is associated with the head; tree equivalence may be
   recorded but is not SHA identity;
6. record Nuxt or other path-filtered non-runs as `NOT_APPLICABLE`;
7. if an intermediate candidate run is used as `CURRENT_REPRODUCTION_EVIDENCE`, preserve
   both its workflow head and actual execution SHA after the final candidate changes;
8. do not claim a prior/intermediate green run satisfies final-candidate adoption gate;
9. independent review evaluates the final documents, provenance and evidence truthfulness,
   not merely whether GitHub displays a green workflow conclusion.

## 12. Closure criteria for reproduction gaps

A `REPRODUCTION_GAP` can be closed only when one of the following is adopted as evidence:

- a clean exact-SHA local procedure with required environment metadata and retained output;
- a GitHub workflow whose actual checkout/execution coordinate is established and whose
  job/step actually exercises the claim; if exact-SHA is required, that coordinate must equal
  the required SHA;
- a documented reason the claim is structural/assumption/direction-only and therefore has
  no executable reproduction obligation;
- an explicitly reviewed decision that the direct reproduction is not required for the
  scoped evidence disposition.

A broad unrelated green suite is insufficient to close a narrow missing-vector gap.

## 13. Exclusions

This protocol does not authorize or define:

- a generic conformance runner;
- new test-generation infrastructure;
- model checking;
- evidence/proof signing;
- a machine-readable evidence schema/generator;
- cross-language/JCS conformance;
- production evidence retention;
- runtime/schema/test/workflow/dependency/timeout modifications;
- P0b or real provider execution.

Any such capability requires a separate need record, scope, exact-SHA evidence and adoption.
